# Better Auth runtime provisioning

`codexia_stage=auth-runtime` is an explicitly approved stage before standalone API activation. Set `codexia_auth_runtime_approved: true` after reviewing the private control-node inputs. The stage verifies the canonical PostgreSQL container. On a pristine database, set `codexia_database_initialization_approved: true` and `codexia_auth_bootstrap_image` to the reviewed immutable Full digest already available to rootless Podman. The canonical initializer applies the application schema first under the shared host lock. The stage then provisions the restricted `codexia_auth_runtime` role, the separate `codexia_auth` schema and protected secrets. The isolated enrollment launcher applies the Better Auth migrations. The public API remains stopped until protected deployment.

The role is restricted to login without superuser, role-creation, database-creation, replication, or RLS-bypass attributes. It has no membership in or grants to other roles, and the stage checks effective access to existing non-system schemas, tables, and sequences. The schema is owned by `codexia_auth_runtime`; the role gets no access to Core or public application tables. PostgreSQL's built-in `PUBLIC` defaults are left unchanged, so the stage does not revoke public schema usage or database temporary-object privileges from other roles. Runtime migrations must be run separately as this role after the schema has been provisioned.

Supply `codexia_auth_database_url_file`, `codexia_auth_secret_file`, and `codexia_oauth_introspection_client_secret_file` as regular control-node files owned by the invoking identity and mode `0400` or `0600`. Supply the OIDC issuer, client ID, and `codexia_oidc_client_secret_file` together when retaining upstream OIDC; omit all three for Passkey-only authentication. The URL must identify `codexia_auth_runtime` on `codexia-db:5432/codexia`, with no query or fragment. Use the same secret bytes for subsequent applies. The stage never rotates or replaces an existing Podman secret; it refuses mismatches. An initial partial secret set can be resumed only while the auth schema does not yet exist. Once a schema exists, every declared secret must exist and match before the stage continues.

Secret bytes are read with `no_log`, passed through standard input, and stored as rootless Podman secrets. The private `~/.config/codexia-auth/runtime.env` contains only nonsecret configuration. The stage leaves the active API and its credentials running. PostgreSQL backups include schemas and rows. PostgreSQL roles and Podman secrets require separate recovery, so escrow the protected values through the approved external secret authority.

## Initial owner and OAuth client registration

For a Passkey-first installation, set `codexia_auth_registration_pending: true`, omit `codexia_oauth_owner_subject`, and provide `codexia_auth_passkey_bootstrap_owner_id`, `codexia_auth_passkey_bootstrap_owner_email`, and `codexia_auth_passkey_bootstrap_owner_name`. Omit all three OIDC settings for a Passkey-only installation. The setup hostname must be a strict subdomain of the staged production authentication hostname (for example, `bootstrap.api.example.test` for `api.example.test`); the browser uses the production hostname as the stable WebAuthn RP ID while the ceremony origin remains the exact isolated setup origin. After `auth-runtime` succeeds, use the pinned SSH management connection as `codexia` and run `~/.local/bin/codexia-grant-passkey-owner --apply <reviewed-full-image-digest>`. Capture the one-time grant from that terminal output; it expires after ten minutes and is stored only as a digest. Forward local `127.0.0.1:8443` to remote `127.0.0.1:8443`, then run `~/.local/bin/codexia-register-auth --apply <reviewed-full-image-digest>`. Open `https://<bootstrap-host>:8443/passkey` in a trusted browser, enter the grant, and create the owner Passkey. Continue to register the reviewed OAuth clients. The result provides the stable owner ID and client identifiers. Close the launcher and SSH forward, then rerun `auth-runtime` with registration no longer pending, the returned owner ID as `codexia_oauth_owner_subject`, and the three passkey-bootstrap variables omitted. Only then follow the separately approved protected push activation.

The OIDC compatibility path remains available for an existing installation: configure all three OIDC settings, provide the immutable owner subject in `bootstrap.env`, and follow the existing provider sign-in flow below. Do not mix OIDC subject bootstrap values with Passkey owner bootstrap values.

1. For the optional OIDC path, choose the production API origin and its exact Desktop and Mobile HTTPS redirect URIs. Generate three distinct client IDs and a high-entropy introspection secret of at least 32 characters. Keep the secret in the protected `codexia_oauth_introspection_client_secret_file`. Set `codexia_auth_runtime_approved: true` and `codexia_auth_registration_pending: true`. Omit `codexia_oauth_owner_subject` on this first pass.
2. Choose a dedicated bootstrap hostname distinct from the production API host. Register `https://<bootstrap-host>:8443/api/auth/callback/workspace-oidc` with the configured IdP client. Protect the registration listener with the pinned SSH management connection. On the operator workstation, resolve the dedicated hostname to `127.0.0.1` and use a TLS certificate for that hostname trusted by the operator browser. Store the certificate and private key as `tls.crt` and `tls.key` under `/home/codexia/.config/codexia-auth`. Store the following reviewed values in `bootstrap.env` in that directory. Use mode `0600` for all three files and ownership by `codexia`.

   ```dotenv
   CODEXIA_AUTH_BOOTSTRAP_ORIGIN=https://<bootstrap-host>:8443
   CODEXIA_AUTH_BOOTSTRAP_OWNER_OIDC_SUBJECT=<immutable-IdP-subject>
   CODEXIA_AUTH_BOOTSTRAP_WEB_REDIRECT_URIS=https://<production-host>/desktop,https://<production-host>/mobile
   ```

   Obtain the exact IdP subject from the approved identity authority. The bootstrap uses the issuer configured by `auth-runtime` and compares the issuer and subject on the verified ID token. The native redirect is `jp.yohn.codexia:/oauth2redirect`.
3. On the pinned SSH connection as `codexia`, forward local `127.0.0.1:8443` to remote `127.0.0.1:8443` and run `~/.local/bin/codexia-register-auth --apply <reviewed-full-image-digest>`. Use the immutable Full image identified by the verified release certificate and already loaded in the rootless Podman store. The launcher checks the healthy token unit and holds the shared host lock. The candidate image runs the existing migration against the isolated auth schema and serves the TLS registration page for at most 15 minutes. Keep the temporary origin off the application Tunnel. In the operator browser, open the bootstrap origin, select the sign-in button, follow the link to the configured IdP, then register the approved clients. The result contains the internal Better Auth owner ID and three public client identifiers. Repeating the operation with identical inputs verifies existing records and returns the same identifiers.
4. Stop the launcher and close the SSH forward. Remove the temporary callback from the IdP and remove `bootstrap.env` and the temporary TLS files from the host. Preserve the production IdP callback `https://<production-host>/api/auth/callback/workspace-oidc`. Rerun `auth-runtime` with the same secret files and client IDs, `codexia_auth_registration_pending: false`, and the returned internal `codexia_oauth_owner_subject`. Follow the [protected push activation](../../docs/deployment/PUSH-DEPLOYMENT.md#first-application-activation), including first-install approvals when there is no prior API. On the isolated test host, verify discovery and an owner-authorized `/api/session` through the deployed instance. Production provider and VM acceptance are tracked in [#168](https://github.com/yohn-jp/codexia/issues/168).

## Existing owner device-loss recovery

Recovery applies only to the exact `CODEXIA_OAUTH_OWNER_SUBJECT` already staged for a healthy Better Auth deployment. Prepare private `bootstrap.env`, `tls.crt`, and `tls.key` files owned by `codexia`, with `bootstrap.env` containing only the dedicated `CODEXIA_AUTH_BOOTSTRAP_ORIGIN=https://<bootstrap-host>:8443`. The setup hostname must be a strict subdomain of the staged production authentication hostname, so the replacement credential remains valid on the production Passkey RP. Use the pinned SSH path and run `~/.local/bin/codexia-grant-passkey-recovery --apply <reviewed-full-image-digest>`. This explicit transaction revokes every owner session and every stored OAuth access and refresh grant, including `offline_access`, then prints one ten-minute grant stored by digest. The transaction also writes a durable `codexia_auth.passkey_recovery_audit` record with the owner ID, timestamp, revocation counts, and grant expiry; the one-use grant is never included in that record. The launcher writes the same sanitized event to the system journal under `codexia-passkey-recovery`, without logging the grant. A second grant cannot be issued until the active grant expires.

Forward local `127.0.0.1:8443` to remote `127.0.0.1:8443`, then run `~/.local/bin/codexia-recover-passkey --apply <reviewed-full-image-digest>`. Open the dedicated HTTPS setup page, enter the one-time grant, and register a replacement Passkey for the existing owner ID. Close the launcher and SSH forward and remove the temporary bootstrap and TLS files. Sign in again through the normal production login page. Recovery does not create an author, delete or migrate manuscript data, change the configured owner ID, or register OAuth clients.
