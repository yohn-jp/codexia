# Codexia — 知識管理と変更レビューの設計

## 位置付け

[情報設計](INFORMATION-ARCHITECTURE.md)、[UX contract](UX-CONTRACT.md)、[MCP-first](../architecture/MCP-FIRST.md) を具体化する再設計提案。Knowledge/EvidenceはCoreのPostgreSQL正本を使う。Storyの実体とKnowledgeのID対応、Native ChangeSet、module proposal、read/write set、version、receiptの責務を変更しない。

## 知識の三つの作業面

**一覧**は作品内の人物、場所、出来事、設定、用語を検索・絞込し、名前、型、状態、利用可能な根拠への導線を表示する。既存の型を表示し、未知の型も失わない。既存APIのページング／上限がある場合は取得範囲を明示し、読み込んだ部分集合を全体と偽らない。

**詳細**は選択した知識を主役とする。名前と状態、別名、属性、関係、根拠、命題を読みやすい順序で表示する。候補を確定する操作と新しい候補の登録を分離し、既存versionチェックと権限を維持する。Story entity IDの手入力は通常導線に置かず、既存Story実体から明示選択できる場合に限って選択UIを使う。同名一致による自動関連付けは禁止する。

**原稿参照**は現在のシーンや選択語句に紐づく知識だけを提示する。対象と根拠の対応を示し、一覧／詳細に移動しても元の本文位置へ戻る。本文未保存や古いRevisionの場合は現在の原稿に結び付いたと誤表示せず、確定済みRevisionへの参照と現入力を区別する。

## 関係の可視化

関係一覧を基準に、必要な範囲だけを局所グラフに投影する。グラフを新たな正本にしない。ノードはstable ID、エッジは既存関係の方向・型・状態・有効範囲で結び、候補／確定／退役を区別する。対象のないエッジ、未ロードの関係、曖昧な別名から事実を推定しない。グラフがない場合も関係一覧で全操作に到達できる。

グラフでは選択ノード周辺の関係を表示し、詳細を開く。全作品の無制限なグラフ描画、距離や中心性に意味を付与すること、ドラッグによる暗黙の関係変更は必須としない。グラフ用ライブラリの採用やサーバーAPIの追加は、既存のprojectionで達成できないことが確認された場合に別途判断する。

## 根拠と視点

引用は原稿の出典、該当Revision、アンカーの状態、リンクの状態を表示する。現在本文と一致するなら該当位置へ移動し、古いRevision・要確認・孤立の場合はその理由と正規の復旧／比較導線を提示する。推測で新しい引用位置を確定しない。

事実、人物の認識、読者への開示、仮説を別の意味として表示する。作者向けの全知識を読者や登場人物の視点に無条件で流用しない。Storyのscope/perspective/snapshotの境界を利用し、利用者が指定した視点と範囲を常に示す。全情報を参照できる作者の画面であっても、作者の確定していない候補を正本の事実として表示しない。

## 変更レビュー

一覧では提案の対象作品、主な対象、由来、状態、変更件数、確認すべき影響を提示する。詳細では対象の名前、変更前後、関係・根拠の追加変更、引用元を読める形で表示する。未知の操作は成功したように要約せず、既存の詳細情報と確認不能の表示を用意する。read/write set、version、operation ID、receiptは技術詳細として展開できる。

| 状態 | 許される操作と表示 |
| --- | --- |
| 提案中 | 内容確認、承認、却下。未適用の正本には反映しない |
| 承認済み | 対象の再確認、既存APIによる明示的な適用。承認だけで成功表示しない |
| 適用済み | receipt、反映対象、更新後の正本を確認する |
| stale／競合／応答不明 | 元のversionと状態を再確認し、利用可能な正規操作だけを提供する |
| 却下／退役 | 通常の正本表示から区別して履歴を保持する |

Native ChangeSetとmodule proposalの権限・原子性・操作単位を変えず、それぞれの正規詳細から処理する。部分承認など既存のAPIが保証しない操作をUIで作らない。Knowledgeの統合は既存previewDigest、projectVersion、明示確認、競合検証を通し、参照移行と統合元退役の意味を提示する。

## 受入

- 原稿から知識、知識から根拠の該当箇所へ戻れる。古い根拠、同名ノード、複数別名、未確定関係、仮説が混同されない。
- ノード・関係・別名・命題の既存候補／確定／却下／退役操作、統合previewと適用結果を失わない。
- グラフと一覧は同じ正規ID、状態、範囲を表示し、視点・snapshot・取得上限を越えない。
- MCPの提案を承認しただけでは正本が変わらず、明示適用後のreceiptと正本が一致する。stale/replay/cross-project/未認可の否定系を維持する。
- Coreでもnative Knowledge/Evidence/ChangeSetを利用できる。任意moduleや外部LLMへの依存を追加しない。

## 知識管理の画面詳細

Desktopの知識作業面は「一覧＋選択対象の詳細」を主領域とし、執筆時の狭い参照ペインとは密度と用途を分ける。選択対象のない時には一覧を重心に置き、詳細に空の巨大フォームを出さない。

```text
┌────────────────────────────────────────────────────────────────┐
│ 作品名   知識               名前・別名で絞る              ＋候補 │
├────────────────────┬───────────────────────────────────────────┤
│ すべて / 人物 / 場所 │ 人物名                           確定     │
│ 候補 / 確定 / 退役   │ 概要 ｜ 関係 ｜ 根拠 ｜ 命題              │
│ 人物A     確定       │ 別名・属性                               │
│ 人物B     候補       │ 主要な関係とその状態                     │
│ 場所C     確定       │ 確定根拠：第一章 / 該当引用 → 原稿         │
│ ...                 │ 要確認の根拠がある場合はその理由           │
└────────────────────┴───────────────────────────────────────────┘
```

### 一覧と詳細の契約

| 項目 | 表示と操作 |
| --- | --- |
| 一覧 | 既存APIが返した名称・型・状態・ID。名前の部分一致、型、状態の絞込。別名で検索できるのは正規の別名データが取得できる範囲のみ |
| 選択 | projectId/nodeIdで固定。同名ノードでも型と所属、必要に応じIDを開示。結果更新で選択が消えた場合は理由を出す |
| 概要 | 名前、型、attributesの意味が判明する項目、別名。未知attributeは保持し、意味不明な内容を物語の事実に加工しない |
| 関係 | 相手名、方向、関係型、状態、有効範囲。既存APIで取得された関係とnodeの対応が取れた範囲のみ表示 |
| 根拠 | 文書階層、引用、revision、anchor/link状態、現在位置の確実性。根拠なしと未取得を区別 |
| 命題 | statement/propositionの表示可能な内容、modality、perspective、状態、根拠。未知schemaは詳細表示で保持 |
| 候補作成 | 名前と型を第一入力にし、既存native候補保存を利用。フォーム確定だけでconfirmedにしない |
| 退役 | 正本からの非表示と物理削除を混同しない。既存APIが許す操作のみ |

一覧の現行取得上限は500ノードである（persistenceNodes）。全体件数が返らない場合は「取得済み最大500件の絞込」と明示し、全体検索の結果0件とは言わない。別名検索や全作品規模の探索には、利用可能な既存Search／Knowledge APIの能力を確認してから接続する。追加APIを当然の前提にしない。件数・最終更新・confidenceなどは取得された実値がある場合だけ表示する。

詳細のタブ切替えは同一nodeIdを維持する。別の詳細に移る時は前の取得を中断し、対象の異なる応答を表示しない。編集中の候補フォームを切り替える時は入力を保持するか明示確認する。既存の確定条件（node、anchor等）を満たさない操作は理由とともに無効化し、UI上の可否だけで認可を保証しない。

### 局所グラフの具体仕様

初期は選択ノードと直接の関係（1 hop）を表示する。方向付き辺には型を示し、選択ノードのラベルは切らない。候補は破線＋状態名、確定は実線、退役／却下は通常表示から除き必要時に明示切替する。線の装飾が物語の重要度や確信度を意味しない。関係先が未取得の場合は未取得として表し、勝手な同名ノードへ接続しない。表示上限は既定で中心＋40ノード程度を目安とし、超過時は件数が分かる範囲で表示省略を示す。自動拡張や全件ロードは行わない。

クリックやキーボードでノード詳細を開き、同じ関係を表形式からも選択できるようにする。パン・ズームは表示の変更のみ。レイアウト・座標をKnowledgeの正本属性に保存しない。グラフ編集のための新規mutationは作らず、関係の追加・変更・確定は詳細の既存API経由とする。

### 原稿から根拠への往復

原稿の語句→候補一覧→node詳細と、知識の引用→該当原稿は別フロー。現在の未保存本文と確定Revisionに由来する根拠を混ぜない。既存 `openNodeEvidence` のdocument、revision、range、quote、confirmed条件を通過した場合にだけ現行本文の選択位置を表示する。古いRevisionは引用と履歴読取りを提示し、現在位置を確定したかのように表示しない。同一文書内の参照でもcomposition/journalのguardを尊重する。

## レビューの画面詳細

```text
┌────────────────────────────────────────────────────────────────┐
│ 作品名   レビュー              提案中 / 承認済み / 履歴          │
├───────────────────────┬────────────────────────────────────────┤
│ 提案一覧              │ 選択提案名   提案中                      │
│ 提案A  人物・関係     │ 対象・出典・影響                       │
│ 提案B  原稿          │ 変更前         変更後                    │
│ 提案C  根拠          │ 引用元 → 原稿                           │
│                       │ 技術詳細 ▸                              │
│                       │                     却下   承認          │
└───────────────────────┴────────────────────────────────────────┘
```

Nativeとmoduleの一覧はsource種別を識別できる状態で並べ、各詳細の処理単位を維持する。件数は取得結果と実状態に基づく。提案の説明はoperationに含まれる対象名・型・変更内容から決定的に生成し、内部LLMを起動して要約しない。タイトルがない時は「知識の変更提案」等の事実に沿った名称を使用する。

| Native操作 | 表示すべき差分・根拠 |
| --- | --- |
| node.save | 名前・型・属性・状態の変更。作成なら変更前は「新規」 |
| alias.save / relation.save | 別名／相手・方向・型、候補→確定などの遷移 |
| anchor.save / mention.save | 引用元・Revision・リンク先、根拠の状態 |
| assertion.save / assertion.link | 命題、視点、根拠、支持等のrole |
| knowledge.merge | 統合元・先、参照移行、別名・関係・命題への影響、退役、競合 |

変更前の値がread setのversionまたはsnapshotに対応して取得できない場合、現在値を変更前と偽らず「変更前を確認できません」と表示する。既存正規APIから取得できる範囲でのみ対比し、技術詳細として元operationと前提を閲覧可能にする。承認前の根拠確認、適用前の状態再確認、適用後の正本更新は既存NativeChangeSetReviewのreconciliationを使う。変更前表示に必要なデータが存在しない場合、新たな永続履歴を本UIの範囲で導入しない。

承認ボタンと適用ボタンを同じ状態で同時に主ボタンとして表示しない。承認済みで初めて適用を表示する。却下は提案の状態変更であり、正本を削除する操作ではない。適用済みだがreceipt未取得なら適用確認済みとreceipt再確認を分離する。応答損失時は同じID/versionによる照合を先に行い、未確認の変更を新規提案として再作成しない。

詳細を離れる際に、原稿の未保存入力・変更提案の現在ID/version・元の一覧絞込を区別して保持する。正本の反映後に未保存原稿を自動上書きしない。既存のrefreshAfterNativeApplyと回復契約に従う。
