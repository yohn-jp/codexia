# 離脱用作品エクスポートの実装契約案

**種別は提案。** [REQ-DATA-006 の正本](../authoring-portable.md#離脱用オープンエクスポート契約req-data-006)が定める離脱用 ZIP について、実装前に確定が必要な HTTP、認可、画面および資源上限を扱う。
対象読者は API、Desktop Web、永続化の担当者。
公開ワイヤへの反映は設計承認後に行う。

## HTTP と認可

[HTTP 契約](API-CONTRACT.md)および [TypeSpec](../../packages/http-contract/src/routes-persistence.tsp)に、次の読み取り操作を追加する。

| 項目 | 提案 |
| --- | --- |
| メソッドとパス | `GET /api/v1/persistence/projects/{projectId}/open-export` |
| operation ID | `persistence_project_open_export_get` |
| 入力 | 既存の `PersistenceId`。本文とクエリーは不要 |
| 成功 | `200`、`application/zip` のバイナリ本文、`Content-Disposition: attachment`、確定済みの `Content-Length` |
| エラー | `400` 入力不正、`401` 認証なしまたは失効、`403` principal 不適格、`404` 作品不存在または作品アクセス不可、`413` 成果物上限超過、`503` 実行枠不足、スナップショット取得失敗または生成期限超過。既存の `ApiError` を使う |
| キャッシュ | `Cache-Control: private, no-store` |
| ファイル名 | `codexia-work-<projectId>.zip` |

[経路認可](ROUTE-AUTHORIZATION-CONTRACT.md)では `OWNER-API` とし、既存の作者認証、オリジン制限および対象作品の認可を再利用する。
公開 reader、MCP grant、OAuth アクセストークンに包括的な作品 ZIP の取得権限を与えない。
資源の割り当ては認可の後に行う。
生成終了時にも応答を書き始める前に既存の認証および作品アクセスの判定を再利用し、失効や取り消しを検出した場合には ZIP を破棄する。

API epoch 4 への追加操作として扱い、既存の archive と import のワイヤ契約を維持する。
旧クライアントは既存操作を使用できる。
Desktop Web が旧サーバーに接続して ZIP 操作が存在しない場合、取得不可を表示する。
互換性は OpenAPI 差分と旧クライアントの回帰試験で検証する。

## 画面

Desktop Web の作品パネル [LIB-01](../design/SCREEN-CONTROL-CATALOG.md)に「離脱用 ZIP をダウンロード」を追加する。
既存の JSON 操作には交換用途を表示する。
操作開始時に選択中の作品 ID を固定し、処理中は同じ操作の再起動を抑止し、キャンセルを提供する。
キャンセルやパネル離脱ではクライアントの受信を中断する。
不完全な応答、期限超過、容量超過、認証失効を画面に表示し、受信完了の状態へ遷移させない。
応答全体を受信し、メディア型と応答長が一致した後にだけ保存用のファイルをブラウザーへ渡す。
状態表示は「ZIP の受信完了」とし、ブラウザーによる保存先とファイル書き込みの成否はブラウザーが所有する。
Native iOS の操作追加は凍結解除後に [Native 契約](IOS-SWIFTUI-ARCHITECTURE.md)で扱う。

## スナップショットと資源上限

既存の永続化 reader が保持する単一の PostgreSQL 読み取りスナップショットから、すべてのページを取得する。
現行文書、履歴、論理削除文書、Knowledge、Evidence および作者所有レコードの投影には既存の読み取り境界と機密除外規約を用いる。
ページ間で順序キーが同値になる場合も、同じスナップショット内の安定した識別子で順序を確定する。
本文および構造化出力の UTF-8 バイト数と SHA-256 は実際に ZIP へ格納する内容から計算する。
パスは作品データから得たタイトルの安全な表示部分に、衝突しない識別子を組み合わせる。
manifest、README および同梱スキーマの公開配布先を作品ポータビリティの正本に記載する。

| 制約 | 提案値 |
| --- | --- |
| ZIP の最終サイズと展開後の合計 | 各 128 MiB |
| ZIP エントリ数 | 32,000。manifest と同梱文書を含む |
| ZIP 形式 | UTF-8 の通常 ZIP。上限を従来の ZIP のサイズおよびエントリ数の範囲に収め、ZIP64 を要求しない |
| 1 API プロセスの同時実行 | 1。待ち行列を持たず、枠が空くまでは `503` を返す |
| スナップショット開始から ZIP 生成終了まで | 120 秒 |
| 応答送信開始から完了まで | 300 秒 |

サーバーはバックプレッシャーのある書き込みで ZIP を生成し、完成済みの一時ファイルだけを送信する。
一時ファイルはプロセスが管理する非公開の一時領域に置き、生成は出力バイト数を計測して上限で停止する。
完成後は DB スナップショットを解放してから送信し、送信中は実行枠を保持する。
生成や送信の失敗、キャンセル、クライアント切断時は読み取りを打ち切り、一時ファイルと実行枠を解放する。
再起動後に残る一時資源の回収も所有プロセスの責務とする。
メモリへの全作品展開は避け、DB ページとファイル書き込みのバッファを上限の単位とする。

容量上限と通常 ZIP の採用は、Windows 標準展開と Desktop Web の全応答受信を同じ範囲で受け入れるための提案である。
上限値は実 DB の計測で検証する。
8 MiB を超える作品と複数ページにわたる履歴を含む成功例に加え、各容量境界、同時要求、同時編集、DB 停止、通信切断、期限超過を検証する。
成功例では外部の ZIP 展開器と JSON Schema 検証器を使用し、得られた全件と UTF-8 本文バイト列をスナップショットに照合する。
異常系は ZIP の受信完了が表示されないことと、一時資源および DB 接続を解放した後に次の要求を処理できることを確認する。
