# Owner-managed OIDC registration and activation contract

**Classification:** Design proposal requiring approval. The accepted [authentication contract](API-AUTHN-AUTHZ.md) and [admin flow](../design/ADMIN-SCREEN-FLOW.md) own the owner-managed OIDC behavior. This proposal specifies how that behavior uses Better Auth SSO, the owner session and the existing PostgreSQL auth schema.

## Provider and owner authority

Better Auth SSO owns OIDC discovery, the authorization-code flow, signature and claim verification, and account finalization. Codexia admits provider management only in the existing normal owner runtime. SAML, organization provisioning, domain-based dispatch and public enrollment are outside the provider surface. The application resolves the provider from its own active selection. A browser cannot select an arbitrary provider or return URL.

Codexia stores staged and active provider references, owner binding evidence and operation state in the restricted `codexia_auth` schema. The referenced SSO provider records hold the provider credentials. There is at most one active managed provider and one current candidate. A candidate has its own SSO record so rotations and failed verification leave the active configuration usable. Public selection uses the existing fixed `codexia-owner-oidc` identity-provider key. The staged and active SSO record references that back it are server-owned. Client secrets enter only the protected Better Auth provider storage. Reads, receipts, exceptions and audit events contain no secrets or raw ID tokens.

The operator supplies the exact permitted external identity-provider origins through protected runtime setting `CODEXIA_OIDC_ALLOWED_ORIGINS`, a comma-separated list of HTTPS origins without paths, queries, fragments or user information. The origin set is separate from the public application origin, from Better Auth trusted origins, and from author permissions. The existing configured issuer remains available during the continuity transition. An empty managed-origin set leaves Passkey sign-in available and keeps managed provider registration unavailable.

For a candidate, issuer metadata must identify the exact configured HTTPS issuer. Discovery and all server-side OIDC requests depend on endpoints validated against the operator-approved origins and the runtime's outbound network restrictions. Enforce the same restrictions across DNS resolution and redirects. Store the validated issuer and use a server-generated application callback. An owner may select only an issuer already within the operator's boundary. The owner session cannot enlarge it.

## Management operations

Add the following operations below `/api/auth/codexia/owner-security/oidc`. Existing owner identity and auth-method availability responses project the same provider state. The management responses use `Cache-Control: no-store`. All mutations apply the existing authoritative owner-cookie policy, exact Origin check and fresh owner authentication. Generated TypeSpec/OpenAPI declarations cover each application operation and distinguish its validation, authorization and precondition responses.

| Operation ID | Method and relative path | Contract |
| --- | --- | --- |
| `owner_oidc_get` | `GET /` | Read active and candidate summaries with their revision, exact issuer, client ID, display name, callback URL, link verification and last check. Distinguish unavailable, unconfigured, operator-configured, staged, verified, active and disabled. Never return a client secret. |
| `owner_oidc_stage_post` | `POST /stage` | Validate the candidate and stage its exact SSO record. Check the expected management revision and associate the durable result with the supplied operation ID. Failed validation leaves the previous active configuration unchanged. |
| `owner_oidc_link_start_post` | `POST /link` | Start owner verification of the current staged revision. Generate a short-lived, single-use transaction and return the provider authorization destination generated by Better Auth. |
| `owner_oidc_activate_post` | `POST /activate` | Explicitly activate the same candidate revision after verified owner linking. Atomically update the active reference and record the result. |
| `owner_oidc_disable_post` | `POST /disable` | Stop admission through the active provider while retaining the verified configuration and the owner's Passkey. |
| `owner_oidc_remove_post` | `POST /remove` | Delete the selected disabled or staged configuration and retire its owner binding. Retain the same internal owner and at least one independent usable authentication route. |

Activating a disabled configuration requires fresh owner authorization and valid verification for that exact record. A change to issuer, client or credentials uses the staging and owner-verification flow. A concurrent revision change fails with a precondition response. A stale revision is a 412, and an operation identity reused for a different command is a 409. After a lost response the client uses the same operation identity or retrieves the management state. The current summaries and latest matching mutation receipt allow the client to distinguish committed and unconfirmed operations. Retrying an operation must never start a second ceremony, activate a replacement record or repeat a completed effect.

Public sign-in uses the existing `POST /api/auth/sign-in/sso` admission. The entry accepts only the fixed public provider key and resolves the active record on the server. It applies the same-origin sign-in boundary and an existing trusted author or console return target. Candidate sign-in starts only through the authenticated management operation.

Provider registration uses the exact callback already admitted by Fastify and Cloudflare, `GET /api/auth/sso/callback/codexia-owner-oidc`. Configure this public URL as Better Auth SSO's fixed `redirectURI`. Use Better Auth's shared callback handler internally so it resolves the stored provider reference from verified OAuth state for either operation. The shared handler's own path remains internal. The return target and provider reference never come from unverified callback input. The public auth-method availability response reflects active admission, independent of whether a candidate SSO record exists.

## Owner binding and continuity

A candidate verification launch must bind the opaque link transaction to the exact initiating owner session, candidate revision and Better Auth OIDC state. Callback processing checks the still-authoritative owner session and the matching verified state. It consumes the link transaction once in the same database transaction used to bind the verified `issuer + sub` to the existing owner. If the installed plugin cannot make this correlation and transaction boundary through its maintained interfaces, the managed flow remains unavailable until that integration is demonstrated. The management API never accepts a browser assertion of the linked subject.

Better Auth's `resolveUser` compares the verified OIDC account key and exact provider reference. It admits active sign-in only for the recorded issuer and subject of the configured internal owner. Candidate admission requires the owner enrollment transaction. A foreign existing account, a different subject, an expired session or a replaced candidate fails closed. Preserve the owner's canonical ID and profile. `disableImplicitSignUp` and the resolver jointly prevent account creation, including explicitly requested signup.

The existing `genericOAuth` provider stays read-only during migration. A verified owner enrolls and explicitly activates the managed provider while keeping a working Passkey. The deployment can retire the legacy sign-in path once that activation and owner continuity have been demonstrated. The operation does not migrate ownership, recreate users, or change the downstream OAuth issuer, grants or client allowlist.

Raw Better Auth provider mutation endpoints are restricted by Fastify admission. Use owner-only `providersLimit` for creation and `guardProviderMutation` for updates and deletion of persisted SSO records. The application verifies the actual owner session before delegating to Better Auth. The plugin's row-level guard must also check the exact record's managed lifecycle and preserve active owner bindings. This defense does not grant the plugin authority to register issuers or manage downstream clients.

## Acceptance

Use a disposable real PostgreSQL auth schema, Better Auth and controlled OIDC providers. Prove owner verification, activation, rotation, disable/re-enable and removal through the Desktop console. Verify that the exact public callback survives the Fastify and Cloudflare path allowlists, that the authorization and token exchanges use the same callback URI, and that active and staged OIDC states never select each other's configuration. Confirm disabled and unverified candidates are not available for normal sign-in. Check that a failure leaves a previously working provider and Passkey usable.

Separately verify that cross-origin and stale sessions, mismatched revisions, unapproved origins, invalid discovery, wrong issuer or subject, duplicate or expired enrollment callbacks and non-owner provider mutations have no provider or account effect. Demonstrate that secrets and raw tokens cannot appear in management responses and audit events. Confirm a directly called route sees the same restrictions as the console, and that restart preserves the exact active and owner bindings. Preserve the current authorization and exact-source certification gates and require the accepted [AUTH-03 tests](API-AUTHN-AUTHZ.md#definition-of-done--executable-acceptance-matrix) before claiming conformance.
