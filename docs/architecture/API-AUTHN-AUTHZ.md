# API authentication and authorization

**Path-by-path normative authorization:** [Route authorization contract](ROUTE-AUTHORIZATION-CONTRACT.md) owns the principal/HTTP method/edge/API resource matrix. User flows and button-level requirements are in [Screen control catalog](../design/SCREEN-CONTROL-CATALOG.md). These contracts specialize, rather than replace, Better Auth and PostgreSQL authorization invariants below.

**Normative authentication contract.** The owner UI's entrypoints and current-vs-target states are defined by [Admin screen flows](../design/ADMIN-SCREEN-FLOW.md); external authentication interfaces conform to [System design](SYSTEM-DESIGN.md). Target requirements in this document are not claims of deployed acceptance.

> This document describes standalone OAuth admission and the accepted Passkey-first requirements. Production rollout evidence is tracked separately.
> This contract specializes [Core architecture](CORE.md) and [Internal boundaries](INTERNAL-BOUNDARIES.md). Better Auth runs inside the Fastify API and supports Passkey sign-in with optional upstream OIDC federation. Cloudflare Access can protect static UI entry as described in [Deployment](../deployment/README.md). Better Auth issues the API credentials for authors and registered MCP clients.

## Decision and trust boundaries

Codexia has one API authorization boundary regardless of client presentation. Desktop Web and installed SwiftUI native iOS clients obtain an **API-specific OAuth access token** from Codexia's embedded Better Auth OAuth Provider. Better Auth authenticates the human through a Passkey or, optionally, a configured upstream OIDC provider. The API authenticates the token, resolves a principal, and independently authorizes each operation and its target objects. It does not delegate data authorization to Cloudflare Access, the Tunnel, a UI bundle, an application signature, or a client-supplied project ID.

| Component | Responsibility |
| --- | --- |
| Cloudflare Access on the static Workers UI | Optional **UI entry** restriction; not an API authorization grant |
| Desktop Web | OAuth public client; obtain API access without bundling secrets |
| Native SwiftUI iOS | Separate OAuth public client; system sign-in and Keychain protected refresh token |
| Optional upstream OIDC provider | Alternative human sign-in; validated assertions are mapped to the existing Better Auth owner, never directly to API author grants |
| Better Auth inside Fastify | Maintain Codexia sessions, OAuth clients/consent, authorization codes, refresh state, API JWT signing keys and OAuth metadata |
| Cloudflare Edge/Tunnel | HTTPS routing and transport to the private API; not proof of application identity |
| Codexia Fastify API admission | Token verification, trusted principal creation, authorization, origin/CSRF rules, request lifecycle, and error handling |
| Persistence/Core | Canonical project-scoped data, revision and proposal enforcement; never accept an unverified client identity |

The upstream OIDC issuer is **deploy-time configuration in the current implementation**. The accepted target allows the owner to stage an issuer within the operator's approved origins. Codexia activates the staged provider only after verification of the existing owner's identity and explicit approval. Better Auth is Codexia's downstream authorization server within the API process; it is not a separate IAM service. A self-hosted backend can change the upstream provider without changing the client protocol.

## Protocol and credential contract

- **OAuth 2.0 Authorization Code with PKCE (S256)** is required for browser and iOS clients using the Codexia OAuth provider. Better Auth establishes the user session by Passkey or optional upstream OIDC federation before the embedded authorization server completes the public-client grant. Register distinct downstream public clients and exact redirect URIs for Web and iOS. iOS invokes the system authentication session, not an embedded WebView login form.
- Upstream OIDC establishes an authenticated Better Auth user. **An upstream ID token or access token is not a Codexia API bearer credential**. Only a downstream access token issued by Better Auth for the configured Codexia API audience may be presented in `Authorization: Bearer`.
- The downstream API resource-server contract is signed JWT access tokens using RFC 9068, including `typ: at+jwt`. Better Auth's JWT plugin publishes signing keys; Fastify verifies signature, issuer, API audience, type, expiry, issue time, token ID, client ID, subject and required scope, then performs confidential online introspection so revoked sessions, refresh state, and exact individual token revocations are reflected.
- When an upstream OIDC provider is enabled, Better Auth's maintained OIDC federation plugin performs Discovery, ID-token signature, issuer, audience, nonce and time validation. For owner-managed OIDC, the protected runtime defines the allowed HTTPS origins and the owner stages provider credentials under that boundary. Do not trust a client-selected issuer during sign-in, accept `alg=none`, or silently fall back when discovery, JWKS or introspection is unavailable.
- Use a stable identity key such as **(`iss`, `sub`)**. E-mail addresses are display/verification attributes, not a secure or stable authorization primary key. In dedicated single-author mode, bind the accepted identity to the explicitly configured owner; a valid token for a different identity does **not** acquire owner rights.
- Prefer short-lived access tokens; clients renew through the Codexia OAuth provider's refresh flow. Never publish refresh tokens in browser assets, logs, the IPA, a CI artifact or GitHub Secrets. Logout/revocation semantics must match the tested provider behavior; JWT signature validation alone cannot guarantee instant revocation.

## API authorization (including BOLA)

Authentication and OAuth scopes are **necessary but not sufficient** for resource access. Central admission resolves an authenticated principal with a trusted author/permission context, then checks the action and actual resource ownership/membership. Do not derive membership, project choice, author approval or permissions solely from `projectId`, a document path, an ID in a payload, `email`, or client-side UI state.

For **every** API and module operation that references a project, document, hierarchy node, revision, proposal, approval, action, snapshot, attachment, Evidence item, job, inbox entry, recent-activity cursor or export:

1. Resolve the caller's authenticated identity and allowed project/resource scope on the server.
2. Check the requested operation's permission **and** membership/ownership of the exact target object, including nested parent relationships. Recheck identifiers in URL, query, body and linked objects; enumeration and bulk endpoints must filter server-side.
3. Reject cross-project and cross-author references without exposing another user's data. A guessed UUID or a successful `GET /api/session` is not authorization.
4. For mutations, preserve the existing PostgreSQL-scoped revision/version preconditions, idempotency identity and atomic write checks. A later change of permissions or object scope must not be bypassed by a previously prepared proposal or stale snapshot.
5. Preserve restricted MCP/external-agent grants. An OAuth bearer for an **authenticated author** must be explicitly distinguished from the existing read/compute/propose-only MCP bearer. Neither a generic bearer, Cloudflare assertion, nor a provider scope string implicitly authorizes `approve`, `apply`, author-only jobs or manuscript modification.

Authorization is enforced on the API boundary and again wherever a transaction must close a time-of-check/time-of-use window. It is not implemented as scattered controller-local `if (owner)` checks. A policy engine (Cerbos/OpenFGA) is not required for the current single-author domain; adopt one only if concrete project-sharing requirements justify it.

## Browser, iOS and transport constraints

The two frontends use the **same API token validation and resource authorization contract**, not necessarily identical login UI or token storage.

- Current production serves the static UI and `/api/*` from one Access-protected hostname. Moving to a separately addressable API requires an explicit Cloudflare routing/Access policy change; **the existing deployment does not already have a public Access-independent API**. Keep the origin and PostgreSQL private throughout the transition.
- The Web UI remains Access-protected as a delivery policy. Its API sign-in is a distinct OAuth flow unless the selected identity provider supports SSO. Browser tokens must not be persisted in `localStorage` or IndexedDB. A same-origin BFF/HttpOnly session may be evaluated if browser token handling warrants it; do not invent a second authorization authority or distribute server client credentials to the browser.
- Cross-origin browser fetches require a deliberately scoped CORS/preflight policy for the configured Web UI origin. Reject wildcard credentialed CORS, reflection of arbitrary origins and unauthorized writes. For cookie-authenticated routes retain CSRF/origin protections; for bearer-authenticated routes do not substitute an `Origin` check for token validation. Differentiate browser navigation, bearer, cookie and MCP credentials without ambiguous privilege promotion.
- Tunnel and Cloudflare WAF/rate limits remain defense in depth. A sideloaded IPA is publicly inspectable and is **not** an authentication factor. No shared client secret or static API owner token is embedded.

## Implementation ownership and dependencies

Fastify admission in `packages/api` owns the request lifecycle, failure semantics, and restricted MCP bearer path. Reuse project authorization, persistence preconditions and the proposal boundary.

Use Better Auth, Generic OAuth and OAuth Provider maintained plugins for protocol, session, client, token and key management. Use the existing `jose` verifier for API JWT profile validation and the official OAuth introspection endpoint for online token status. Do not hand-write discovery, token issuance, signature verification or a second auth router. Reuse Fastify 5 and the existing API admission boundary.

Better Auth admits the enrolled owner through registered author clients and admits MCP clients through their explicit project assignments and limited scopes. Verification and introspection outages fail closed.
OWNER-API and MCP-CLIENT use the same resource-server verifier and read the space-delimited `scope` claim issued by Better Auth. Each applies its own subject, client, and scope policy before online introspection. The API distinguishes invalid and inactive credentials from unavailable signing keys and unavailable token status.

### Better Auth standalone owner bearer

Standalone Better Auth requires `CODEXIA_AUTH_DATABASE_URL`, `CODEXIA_PUBLIC_ORIGIN`, `CODEXIA_AUTH_SECRET`, `CODEXIA_OAUTH_INTROSPECTION_CLIENT_ID`, `CODEXIA_OAUTH_INTROSPECTION_CLIENT_SECRET`, `CODEXIA_OAUTH_OWNER_SUBJECT`, and comma-separated `CODEXIA_OAUTH_OWNER_CLIENT_IDS`. The `CODEXIA_OIDC_ISSUER`, `CODEXIA_OIDC_CLIENT_ID`, and `CODEXIA_OIDC_CLIENT_SECRET` settings are configured together only for upstream OIDC. `CODEXIA_API_AUDIENCE` defaults to `<public-origin>/api`. Standalone MCP uses a separate client allowlist and explicit project assignments for the limited `mcp:read`, `mcp:compute`, and `mcp:propose` scopes. Supply secrets through protected runtime configuration. The owner subject is the stable Better Auth user ID associated with the enrolled Passkey or linked OIDC account. The API requires both verified owner identity and a registered public client for author scope.

The Better Auth Generic OAuth callback route was observed in the signed-out PostgreSQL fixture as `<CODEXIA_PUBLIC_ORIGIN>/api/auth/callback/workspace-oidc`. Register that exact HTTPS URI with the selected upstream provider for the configured public origin. The fixture used loopback HTTP only for its local synthetic IdP/API and does not qualify a production provider configuration. Google Workspace is the first intended provider; no Google client secret, provider-side callback registration, or real Google login has been configured or tested in this change.

Auth tables live in the independent PostgreSQL `codexia_auth` schema. The runtime database role `codexia_auth_runtime` must own that schema and have only required database/schema privileges; it must have no `CREATE` on `public` or data privileges on non-auth tables/sequences. Production startup does not run migrations or create roles/schemas. After schema and grants are provisioned, run `pnpm --filter @codexia/api build`, then `pnpm --filter @codexia/api migrate:auth -- --apply` with protected `CODEXIA_*` runtime configuration loaded. The command verifies `current_schema() = codexia_auth`, `current_user = codexia_auth_runtime`, and schema ownership; calls Better Auth's official `$context.runMigrations()`; creates the app-owned `oauth_jwt_access_token_revocation` table in the same schema; and never creates a role or schema.

Revocation rows expire logically at their token's `expires_at`; API admission and introspection ignore them as soon as that timestamp passes. The revoke handler also removes expired rows when it records a new revocation, but idle deployments cannot rely on that opportunistic cleanup. Build the API and run `pnpm --filter @codexia/api prune:auth-revocations -- --apply` during the existing low-traffic database maintenance window, with the protected auth database configuration loaded; weekly is the recommended operator cadence. The command requires the `codexia_auth_runtime` role to own and use `codexia_auth`, and deletes only expired rows. It does not require stopping API admission. No scheduler invokes it: if an installation is idle or an operator skips maintenance, expired rows remain stored but have no authorization effect until the next explicit prune.

Register distinct Web and iOS public OAuth clients with exact redirect URIs, `token_endpoint_auth_method: none`, Authorization Code + Refresh Token, PKCE required, the exact API resource, and only intended scopes. Register a separate confidential client for API introspection; keep its secret only in protected runtime storage. Set `CODEXIA_OAUTH_OWNER_SUBJECT` to the established internal owner user ID and `CODEXIA_OAUTH_OWNER_CLIENT_IDS` to the registered public client IDs. Unauthenticated dynamic registration is disabled.

Clients send `Authorization: Bearer <access_token>` to the existing `/api/*` API origin. The token grants the configured internal owner the existing author operations, and `/api/session` reports `{ authenticated: true, authorScope: "owner" }`. Other subjects and missing scopes receive 403. Invalid access tokens and unknown keys receive 401. Unavailable verification or introspection dependencies fail closed. PostgreSQL project and object transaction guards apply to every author operation.

Better Auth 1.7.26's official revocation endpoint returns `unsupported_token_type` for a signed JWT access token. The existing endpoint is wrapped by a narrow RFC 7009 adapter: after Better Auth authenticates a registered client, the adapter verifies the RFC 9068 token and records its exact issuer, `jti`, client, subject, session, and expiry in PostgreSQL. It returns the RFC success response for unknown and foreign-client tokens without recording them. API admission and OAuth introspection consult that exact record, so revoking one access token does not revoke sibling tokens or the login session; expiry and logout retain their existing behavior. The PostgreSQL fixture verifies token denial, inactive introspection, client ownership, harmless unknown responses, expired-token handling, and no sibling-token effect.

Cross-origin Web requests are optional and use `CODEXIA_CORS_ALLOWED_ORIGINS`, a comma-separated list of exact normalized HTTPS origins. An unset list permits same-origin requests only. The API returns `Access-Control-Allow-Origin` only for a configured exact origin, limits preflight methods to the requested supported method, and allows only the request's explicitly listed supported headers. It never enables credentialed CORS or reflects arbitrary origins. Cross-origin protected API calls use bearer authorization and omit browser credentials; any cross-origin cookie is denied. `Authorization`, `Content-Type`, `Idempotency-Key`, `X-Client-Id`, `X-Codexia-Recent-Activity-Order`, and `Prefer` are the supported request headers. Cookie-based mutation remains same-origin protected.


## Accepted target: Passkey-first authentication and identity management

**Status: normative target.** Existing API protocol, principal, ownership and manuscript boundaries apply. The scope is a single standalone owner, excluding multi-tenant identity, SAML, SCIM, new organization roles and a separate identity service.

### Outcome and identity invariants

- A person never enters, copies, generates, or persists a static Codexia API token to use Desktop Web, native iOS, or remote MCP. "Remove access tokens" means **remove manually managed long-lived standalone tokens**; short-lived OAuth access JWTs, rotating refresh tokens, server-side sessions and OAuth grants remain protocol requirements.
- Better Auth in the existing Fastify process and PostgreSQL `codexia_auth` schema is the single standalone identity authority. A durable internal Better Auth `user.id` is the accepted owner subject. Passkeys and optional OIDC `(issuer, subject)` accounts attach to that same internal user; changing a device or an IdP does not change author/project ownership.
- Passkey is the default human sign-in, independent of any OIDC service. OIDC is optional, must be explicitly configured by the already authenticated owner, and must never be needed for Passkey-only startup. No public self-registration, unapproved owner creation, implicit email-account linking, automatic second owner or downgrade to legacy token login.
- Retain distinct registered OAuth public clients for Web and iOS, short-lived API-audience `at+jwt` tokens, PKCE S256, signed metadata, audience and scope checks, online introspection, exact-token revocation and the existing CSRF/origin boundaries. The browser retains the current in-memory access token; the iOS target uses OS system authentication and a Keychain-protected refresh token. Neither needs a new native Passkey bridge or a cookie-based API rewrite.
- Better Auth is the OAuth authorization server for the MCP Streamable HTTP protected resource. Keep the existing `oauthProvider()`, `mcp:read` / `mcp:compute` / `mcp:propose` limits, client allowlists, project assignments and `external-mcp` principal. MCP admission relies on the API's OAuth checks.

### Maintained Better Auth components and persistence

| Area | Chosen authority / bounded change |
| --- | --- |
| Passkey | Add the official `@better-auth/passkey` server and client plugins and their maintained `passkey` table via the existing explicit `migrate:auth` workflow. Configure exact HTTPS origin and stable RP ID derived from the public authentication hostname; never derive trusted RP/origin from arbitrary request headers. Enforce user verification on registration and authentication. |
| OIDC federation | Replace the fixed mandatory `genericOAuth` provider with the maintained `@better-auth/sso` OIDC registration/management path when fully migrated; there must not be two independently writable provider authorities. Do not enable SAML or organization provisioning. The single owner's provider selection uses a fixed registered provider ID, not email-domain guessing. |
| Downstream OAuth | Keep `@better-auth/oauth-provider` and JWT signing, existing consent and client registry, resource metadata, introspection, token revocation and shared API admission. Do not install `@better-auth/mcp` alongside `oauthProvider()`; replacing the provider is a separate, explicitly justified migration, not a prerequisite. |
| Users / accounts | Preserve the internal owner user ID and bound OAuth owner subject. Store identities as exact `(issuer, sub)` links; no email match, IdP claim alone, client-supplied owner, or `accountLinking.trustedProviders` grants ownership. |
| Config / secrets | `CODEXIA_OIDC_*` cease being mandatory startup inputs in the target. Public origin, owner ID, signing/DB secrets, downstream client IDs, API resource and allowed external IdP origins retain explicit operator authority. Persist provider records in the restricted auth schema using maintained plugin tables. Secrets are write-only in UI/API responses, never emitted in logs, frontend builds, telemetry or public artifacts; protect database/backup access and allow credential rotation. |
| Schema / lifecycle | Keep explicit offline schema migrations and least-privilege `codexia_auth_runtime`. No startup migration, new database, second auth router, hidden fallback or Core schema mutation. Existing auth rows, OAuth clients, signing keys, sessions and recovery journal remain intact across migrations. |

For OIDC runtime registration, constrain Better Auth SSO's defaults: only the exactly verified owner may register/update/delete a provider (`providersLimit` and `guardProviderMutation`), initially **at most one active provider**; arbitrary authenticated users must get 403. Set `disableImplicitSignUp` **and** use `resolveUser` to reject unknown users even if a caller submits `requestSignUp: true`. A link is permitted only for an owner-initiated, short-lived, single-use, session-bound enrollment transaction and a fully verified IdP `issuer + sub`; return the existing internal owner ID and preserve the profile. Reject subjects already linked to other users and unapproved issuer changes; require a fresh owner reauthentication for trust-boundary changes. Provider deletion and rotation must not silently replace owner identity.

SSO Discovery fetches may require an IdP origin in Better Auth `trustedOrigins`. That list is also used for CSRF/redirect trust: **never automatically append an arbitrary URL from the settings form**. Accept only operator-approved exact HTTPS issuer origins for registration and server egress; reject loopback, link-local, private-address, userinfo, fragments, redirect chains and DNS rebinding to forbidden ranges. Validate exact Discovery issuer and signed ID-token issuer, audience, nonce, time and subject. If the pinned plugin cannot implement these controls without broadening CSRF trust, block new provider activation rather than substituting custom token verification or trusting the UI. The issuer origin allowlist is a deployment-controlled precondition displayed by the form.

[Owner-managed OIDC registration and activation](OWNER-OIDC-MANAGEMENT-CONTRACT.md) defines the management operations, exact provider selection, enrollment transaction and acceptance evidence. Availability requires proof that maintained Better Auth interfaces bind the initiating owner session, the candidate revision and verified OIDC state, then consume the enrollment and bind the upstream account in one PostgreSQL transaction.

### First-owner enrollment, ongoing credentials and recovery

1. An already established Better Auth owner signing in through the current OIDC link may add a Passkey to their **existing** Better Auth user. The owner mapping is checked before and after the WebAuthn ceremony; no new user row or project ownership mapping is created.
2. **Agreed target:** On an explicitly approved fresh installation, Ansible initiates creation of a CSPRNG-backed 256-bit **single-use, 24-hour** setup key, but does **not** register an owner. The operator delivers the key to the intended person through a protected out-of-band channel. The person opens the Cloudflare Workers Static Assets `/console/setup` screen, supplies the key and explicitly completes the maintained Better Auth Passkey ceremony. The API confirms the assertion and atomically binds exactly one internal owner and consumes the key in PostgreSQL. The existing local-CLI/temporary-container/SSH-forward registration is current implementation, **not** the target user journey. No public self-registration, reusable bootstrap API token or owner creation on first anonymous visit.
3. Normal Passkey registration requires an authenticated session, owner authorization and fresh verification. Provide listing, naming, adding and removal. Do not allow the last usable login method to be deleted while active. Require either a second independently usable Passkey or a verified linked OIDC fallback before declaring migration complete; a hardware key is supported but never required solely to enable login.
4. Device loss recovery is **operator-mediated**, not an evergreen emergency bearer. Through the existing protected VM administration path, an explicit audit-logged recovery transaction revokes the owner's sessions and affected grants, issues one short-lived enrollment challenge tied to the same owner ID and consumes it once. No endpoint accepts email ownership, a static API token or an arbitrary IdP subject as recovery evidence. Failure does not delete manuscript data or change author identity.
5. Reauthentication is mandatory for passkey deletion, provider issuer/client changes, and changing session/consent policy. Session invalidation and refreshed client grants must match the actual Better Auth behavior; never report a JWT as revoked merely because a UI logout occurred.

### Initial setup admission and installation state contract

- **Boundary:** Workers serves only the UI and `/console` routes. The existing VM Fastify/Better Auth process owns setup admission, Passkey registration and all writes to the restricted `codexia_auth` schema. The setup-only runtime is the same authenticated backend with a restricted route set, **not** a new IAM server, independent author database, second token authority or publicly exposed management SSH.
- **DB state machine:** `NEW_APPROVED` (explicitly new and genuinely empty), `SETUP_PENDING` (key issued, no owner), `OWNER_ENROLLED` (owner and credential committed, normal API not yet activated), `ACTIVE`, and `RECOVERY_REQUIRED` or `BLOCKED`. These are logical contracts, not necessarily new database enum values. State comes from the trusted PostgreSQL identity and deployment record, never a client flag or whether the VM filesystem appears empty. Once any owner exists, every first-owner create operation fails closed regardless of Ansible reruns or VM replacement.
- **Key issuance:** A reviewed, explicitly approved Ansible bootstrap action invokes a bounded application initialization operation after verifying the database is new and no owner/registration exists. It obtains 32 CSPRNG bytes, persists only a high-entropy digest, issue/expiry/consumed metadata, and exports the raw secret **only once** through a protected operator-to-owner handoff. Idempotent reapplication cannot rotate, print, reset or reopen an existing key. No raw key in Git, Podman env, Workers artifacts, Ansible facts, Terraform state, CI logs, URL, referrer, browser persistent storage or analytics. Expiry or lost-key reissue requires independent operator approval, with the old grant revoked; **never** automatic owner recreation.
- **Browser admission:** The key is entered in a dedicated form; request transport must be HTTPS, exact allowed origin, CSRF-protected and rate-limited. Validation creates at most a short-lived **setup-scoped** transaction, not a standard bearer token/owner session. The browser then explicitly invokes the official Better Auth WebAuthn creation ceremony with RP ID/origin and user verification enforced. The backend holds the single-owner invariant under concurrent requests, ties a ceremony to the exact pending transaction and consumes the grant with the verified owner creation. No partial user row receives owner authorization, even if a request is interrupted. Duplicate/expired/replayed grants fail; an ambiguous network result is resolved through server state, not assumed to have failed.
- **Setup-only exposure:** Before full activation, Cloudflare Tunnel may transport the *narrow* setup endpoints required for state, key validation, WebAuthn registration and readiness. All manuscript APIs, MCP, normal author mutations, unrestricted OAuth dynamic client registration and infrastructure controls are denied. The static UI and these endpoints must be reachable through an explicitly reviewed Cloudflare Access/path policy; **Access identity never replaces the setup key**. WebAuthn RP ID and public origin must be identical to the eventual production owner sign-in contract. Publishing the Workers asset alone does not expose a backend endpoint.
- **Client provisioning:** Once owner registration is verified, the same API/Better Auth identity authority registers or checks the predefined Web/iOS public PKCE clients and the confidential introspection client against reviewed redirect/resource/scope inputs. Secret-bearing setup is server-side; neither Ansible-generated owner records nor browser-provided arbitrary client definitions are allowed. Owner-managed optional OIDC can be configured after normal login through `/console/identity`. Full API activation still requires the separate protected delivery approval, compatibility/certificate validation and encrypted backup.
- **Recovery:** On a replacement VM with restored PostgreSQL/auth data, reuse the identical Better Auth owner ID, Passkeys, sessions/key material as applicable, approved OAuth clients, auth schema and protected secrets. Do **not** mint a fresh first-owner grant. Loss of Passkey without loss of the owner database uses the separately authorized existing-owner recovery transaction, revokes affected sessions/grants and restores a credential to the **same** owner; it never creates a new owner. Unknown or partially restored data blocks both normal activation and first-owner registration.

The route and view/operation/error UX are owned by [Admin screen flows](../design/ADMIN-SCREEN-FLOW.md); the SSH-to-Ansible prerequisites, setup-only-to-production transition and existing-data recovery are owned by [Initial deployment flows](../deployment/INITIAL-DEPLOYMENT-FLOW.md). Existing SSH-forward enrollment commands remain documented as current behavior until replaced; a design change alone is not proof of functioning production setup.

### Settings UX and API behavior

**Target routing:** Cloudflare Workers Static Assets hosts `/console` (owner home), `/console/setup` (first owner only), `/console/security` (Passkeys and sessions), `/console/identity` (linked IdP and OAuth client/consent management), and **`/console/backups` (owner-managed S3 backup destination, verification, run status and recovery evidence)**. The backup console routes use OWNER-SESSION and server-side fresh reauthentication for credential changes, activation/disable and manual runs; they do **not** issue OPERATOR, SSH, Podman, PostgreSQL administrator, or S3 IAM privileges. [Backup console contract](BACKUP-CONSOLE-CONTRACT.md) owns those details. An owner OAuth API bearer or MCP token never grants access to these routes. Reuse the existing Desktop settings design and shared typed commands/policy; the former Mobile settings UI has been removed and is not a compatibility target. The currently implemented Desktop dialog remains until its entrypoint is moved or linked to the console. Browser WebAuthn launches only on an explicit user action; the accepted iOS target uses native system authentication. A missing authenticator or provider does not erase local writing once already authenticated.

| Screen / state | Required user-visible actions and explanations |
| --- | --- |
| Passkeys | List nickname, creation / last-use information **when provided** by Better Auth, and device metadata when reliable; add, rename and revoke each; show the current device when known, never invent its identity; explain failed/cancelled WebAuthn and reauthentication. |
| Linked sign-in methods | Show Passkey and optional OIDC independently, including a clear "not configured" state, link verification, current usable fallbacks and the consequence of disabling a method. |
| Sessions / OAuth consents | Show active sessions, revoke a selected session or other sessions, inspect/revoke own downstream OAuth app grants; explain that token invalidation may require actual revocation and introspection, not just local UI cleanup. |
| Provider management | Owner-only: display name, exact issuer/discovery endpoint, Client ID, **write-only** Client Secret, generated read-only callback URL, approval/verification state and last check, test connection, stage changes, activate, rotate secret, disable and remove. No state change or secret display until explicit commit/confirmation. |
| Failure / lockout | Distinguish unsupported WebAuthn, cancelled challenge, wrong origin, expired session, unverified issuer, invalid credential, last-method removal denial and OAuth outage. Preserve unsaved manuscript drafts through login or expiry transitions; never present a partial config as active. |

Server policy is authoritative: deny non-owner provider and passkey mutations even when invoked without the UI; enforce same-origin session + CSRF and recent owner reauthentication. Provider staging and activation must be atomic and auditable, must not break currently working Passkeys, and a failed connection test must leave the previous active provider unchanged. Do not store provider secrets or recovery grants in browser storage. Keep the OAuth client/consent UI read-only or revoke-only until existing environment-backed client allowlists and project assignments are replaced in **one** authoritative migration; do not introduce a second writable permissions store.

### Edge exposure and access control (deployment prerequisite, not implied by code)

The existing production deployment uses an Access-protected hostname and an origin-side Access assertion. That is **not already** an Access-independent API. Before declaring remote MCP or native OAuth accepted, update the Cloudflare/Tunnel and origin policy explicitly:

- The public HTTPS `/mcp` protected resource, `/.well-known/oauth-protected-resource` variants, OAuth authorization-server/OIDC discovery, JWKS, and required `/api/auth/*` endpoints must be reachable **without Cloudflare Access cookies, service tokens, HTML login redirects or JWT assertions**. The API's own authentication, rate limiting, input validation and OAuth protocol responses remain mandatory. Authenticated `/api/*` data operations must never become anonymously authorized.
- Prefer explicit **path-scoped Access application overrides** on the existing origin when they can be verified end-to-end; a separate API hostname is an alternative only with explicit Web same-origin/PKCE, CORS, session, callback, mobile and rollout changes. Do not assume merely adding a Worker/Tunnel route bypasses an Access application. Maintain the current static UI entry policy unless separately approved.
- The agreed `/console/setup` design uses the same production HTTPS origin for WebAuthn and connects the Worker UI to a **setup-only** Fastify mode before the author API is active. ## Required acceptance evidence for implementation

- Better Auth authenticates the existing owner through Passkey without any upstream OIDC setting and issues API-audience OAuth access tokens through public-client Authorization Code + PKCE for Web and iOS; both call the same protected API with equivalent results.
