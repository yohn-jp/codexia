# Backup Console executor provisioning and recovery

**Status. Design proposal pending approval.** The deployed contract remains the approved lifecycle from #950, the Backup Console contract and the existing Ansible delivery path. This proposal covers provisioning and recovery of the present v2 backup executor. The backup product evaluation has a separate scope. [#950](https://github.com/yohn-jp/codexia/pull/950) · [Backup Console contract](../architecture/BACKUP-CONSOLE-CONTRACT.md) · [Deployment lifecycle](DEPLOYMENT-LIFECYCLE.md) · [IaC](IAC.md)

## Current deployment gap

The Ansible transaction installs the backup producer, runner and launcher. The long-lived executor and deploy control CLI also need a private database connection, least-privilege login roles, the operational schema, a sealing key and operator configuration. The API needs its own constrained login, the public half of the sealing key and the operator policy. The installed API Quadlet supplies none of those inputs. The PostgreSQL Quadlet attaches to the internal data network and keeps its Unix socket inside the container. A host executor has no configured route to that PostgreSQL instance. [Deployment helper installation](../../deploy/ansible/deploy-prepare.yml) · [PostgreSQL Quadlet](../../deploy/quadlet/codexia-db.container) · [API Quadlet](../../deploy/quadlet/codexia-api.container) · [Existing operator settings](../../deploy/backup/CONSOLE.md)

An installation must reach ACTIVE with no S3 configuration or recovery receipt. The operator must then be able to enable the existing Console backup runtime and the owner must be able to configure a destination before R8 is enabled. This applies to current installations that reached ACTIVE before the runtime was provisioned as well as new installations. ## PostgreSQL access for the host executor

| Option | Fit | Verification needed |
| --- | --- | --- |
| **Use a PostgreSQL Unix socket in a private shared directory** | Keeps the executor and lock on the VM and preserves the isolated data network. The API can keep its existing container-network connection. | Confirm rootless UID mapping and access after reboot. Shared socket authentication must enforce SCRAM for the dedicated executor login and prevent unauthenticated access to any other login. PostgreSQL local HBA rules cover all Unix sockets, so verify the existing database bootstrap, backup and recovery commands with the resulting rules. |
| Bind PostgreSQL to a loopback-only host port | Lets the host driver use the existing TCP authentication contract and avoids a shared filesystem. It adds a DB listener reachable by VM-local processes. | Prove the bind remains loopback-only under the canonical rootless network runtime, including after reboot. Test against API and other Podman namespaces as well as the VM. |
| Launch the host executor in Podman's rootless network namespace | Can avoid adding a published port or shared socket. It couples the host worker to Podman namespace and DNS lifecycle, including runtime recovery. | Prove database address identity, name resolution, S3 egress, systemd interaction and host-lock behavior after Podman or VM restart. |
| Run the Node executor on the internal container network | Uses the image's installed runtime and direct PostgreSQL connectivity. Its approved work still requires the host runner, systemd and inherited host lock. | This would require an additional host invocation mechanism or broader Podman privileges. The current contract provides neither. |

Select the private authenticated Unix socket for a disposable-host implementation spike. Treat existing in-container local authentication and rootless ownership as release conditions. If the spike cannot preserve either, return to design review for the loopback-only alternative. Keep the current PostgreSQL service and database, the two existing capability roles, and operator policy as the authorities for data access. [PostgreSQL socket settings](https://www.postgresql.org/docs/17/runtime-config-connection.html) · [PostgreSQL HBA rules](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html) · [PostgreSQL password authentication](https://www.postgresql.org/docs/17/auth-password.html) · [Podman rootless network namespace](https://docs.podman.io/en/latest/markdown/podman-unshare.1.html)

## Provisioning with the existing deployment authority

Have the existing Ansible flow install or adopt the two database login roles, apply the reviewed operational schema or applicable upgrade, and verify effective role privileges. Keep the executor login and sealing private key in VM-local protected settings and independent recovery custody. The API gets only its own login and the public key. Use the existing certified Full image as the source of executor code and its runtime dependencies. A private host installation can be extracted from that exact digest. It needs proof that the compiled runtime and locked dependencies run on the canonical VM, and that interrupted replacement selects one verified installed version. [Role grants](../../deploy/backup/operational-schema.sql) · [Role verification](../../deploy/backup/verify-console-roles.sql) · [Full image build](../../Dockerfile.backend)

Determine in implementation review how to deliver local platform preparation on new installations while leaving provider setup and recovery acceptance to ACTIVE. For an existing ACTIVE installation without the runtime, use the existing protected Maintenance lane to enable it without changing the running image, the application ledger or the owner. A restart required for API configuration remains a protected transaction under the existing host lock. Existing installations with active configuration, sealed credentials or independently retained backups must be adopted in place. Repeating Ansible convergence must preserve role passwords, key identity, settings and pending operation records. New provider settings and credentials belong in the normal Console after operator provisioning. [Deployment lifecycle](DEPLOYMENT-LIFECYCLE.md) · [Existing Console provisioning](../../deploy/backup/CONSOLE.md)

The executor and deployment control use the same private settings and host lock. Reboot recovery belongs to the existing VM runtime and durable PostgreSQL queue. Maintain the current background executor as the one schedule work owner and retain approved maintenance windows. The R8 path remains a compatible image deployment with the pinned active Console revision and verified off-VM result. ## Restore before the executor resumes

The current v2 dump includes the operational schema when it exists. Because the producer takes the snapshot before publishing the remote receipt, the selected snapshot may contain its own RUNNING row without that receipt. The durable in-flight index prevents a new run while such a row is unresolved. The VM-local transaction records that would ordinarily guide reconciliation may have been lost with the VM. Remote preservation and successful restore are evidenced separately. [Backup producer](../../deploy/backup/backup.sh) · [Operational schema](../../deploy/backup/operational-schema.sql) · [Executor startup](../../packages/api/src/backup-console-executor.ts) · [Console control](../../packages/api/src/backup-console-control.ts)

Keep the executor stopped while the recovery operator restores and verifies the data, roles and independent secrets. Use the protected receipt and selected artifact to reconcile the original run ID, source identity and manifest checksum under the existing lock. Update only the recovered records that the evidence can identify. Preserve ambiguous pre-loss in-flight work as unresolved and require operator disposition before starting the worker. A newly started worker must never replay a pre-loss backup, configuration mutation or expired maintenance slot merely because it appears queued in the snapshot. Use the existing run journal and restore evidence model. Design review must settle the exact disposition and audit retention of unresolved rows, as well as how the operator imports off-VM proof for a run whose terminal state postdates the dump. ## Acceptance before selecting a topology

- A fresh install reaches ACTIVE and the owner can reach its normal Console before any provider credential, public age recipient or independent restore evidence is available. The operator provisions the backup runtime on a disposable new VM and an existing ACTIVE VM. Reapply provisioning and compare data, roles, keys and all pre-existing activity.
- Verify the PostgreSQL endpoint from the selected worker boundary and deny unauthorized local and API-side principals. Keep PostgreSQL unreachable from other hosts. Prove least-privilege roles, private key isolation, verified production runtime origin, restart and reboot behavior.
- Configure and activate a destination in the Console. Exercise manual execution and compatible update on the same VM runtime and lock. Verify off-VM readback, absent configuration and required-provider failure, and interrupted backup and rollout recovery.
- Restore the selected backup on a separate disposable host with an independently obtained receipt and necessary secrets. Include a captured RUNNING deployment backup, a queued configuration operation and an expired scheduled slot. Prove the journal disposition with a restored PostgreSQL database, verify API readiness and confirm that a newly approved run completes through the same Console.
- Record synthetic exact-source CI evidence separately from actual provider, VM and independent recovery acceptance.
