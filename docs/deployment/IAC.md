# Standalone infrastructure as code

**Normative target architecture.** Ansible is the single desired-state authority for the Codexia-managed configuration of a standalone VM. The implementation is being migrated from the existing updater-only playbook; the target requirements below are binding for new implementation, not a claim that they are already implemented. Hosted runtime, hypervisor provisioning, initial OS installation and external infrastructure are out of scope.

## 1. Ownership and boundaries

| Authority | Responsibility |
| --- | --- |
| Ansible (`deploy/ansible`) | Converge and verify all Codexia-owned host configuration, dependencies, rootless service identity, files, secrets, networks, persistent volume identities, database, Tunnel connector, updater/proxy, backup and maintenance entrypoints. Adopt existing installations without destroying data. |
| Quadlet (`deploy/quadlet`, updater templates) | Declarative local runtime representation consumed by rootless Podman/systemd. Ansible installs and verifies static units; the updater alone generates writer slots. Quadlet files are not a second desired-state authority. |
| Standalone updater | Authenticated release admission, exclusive writer fencing, slot generation, route/journal, compatibility checks, recovery and rollback. Ansible invokes existing locked operations; never creates a competing writer, edits a journal or changes the route independently. |
| Terraform (`deploy/cloudflare/terraform`) | Cloudflare Access, DNS, remote Tunnel configuration, Worker routes. Existing account-owned policies and shared zone rules retain their owners. Ansible manages the VM-side connector, not Cloudflare resources. |
| GitHub Actions | Exact-source verification, immutable OCI publication, protected signing/channel maintenance and independent static frontend delivery. No VM SSH credentials or automatic infrastructure apply. |
| PostgreSQL | Sole manuscript authority. Data and operational journal are durable runtime state, not desired-state templates. Neither Ansible nor CI overwrites them. |

The required end state is a single reviewed Ansible entrypoint plus explicit lifecycle operations, using private inventory/secret inputs. Routine VM administration must not require copying files, issuing ad hoc Podman/systemd commands or manually editing units on the host. Emergency break-glass recovery remains documented, audited and reconciled via Ansible before returning to normal service.

## 2. Supported baseline and inventory

The starting boundary is an SSH-reachable Linux VM with verified host key, a bootstrap identity able to perform narrowly scoped privileged setup, working package repositories and network access. The initial supported host implementation is Ubuntu 26.04 amd64, systemd, cgroup v2, rootless Podman with Quadlet support, and Node.js >=22. Unsupported distributions or missing required capabilities fail before mutation. Additional OS support needs explicit implementation and acceptance. The VM image, SSH trust enrollment, external backup destination and secret authority remain external inputs; do not manufacture or guess those values.

Use a single validated inventory schema with separate nonsecret configuration and private credential references. Inventory declares:

- service user, UID/GID policy, home, rootless subordinate ID allocation/validation, package/toolchain versions or supported version constraints, lingering, directory ownership and required host capabilities;
- the existing network/volume identities and security constraints, database and cloudflared immutable image digests, selected Core/Full profile, signed backend release reference, immutable proxy image and selected browser-auth configuration;
- explicit permitted runtime options needed by the profile (resource limits/tmpfs and the read-only model cache). `modelCachePath` is limited to `/var/cache/codexia/models` and its descendants; this dedicated artifact tree stays outside authoring storage, and source paths cannot traverse symlinks. No arbitrary shell, environment passthrough or unrestricted host paths;
- protected input references for auth token, Tunnel token, independent PostgreSQL admin/app/preflight passwords, GitHub read/registry access where required, scoped Access probe credentials, pinned Ed25519 public key, backup recipient and destination. The signing private key stays in the protected publisher; the recovery private key stays on the isolated recovery host;
- backup/restore policy, retention responsibility, maintenance approval, and desired polling state. Approval flags authorize operations, not proof of execution.

Ansible must validate types, absolute paths, image identity/profile, credential separation, required options and ownership before disruptive work. No real inventory, private URLs/host aliases, tokens, keys, password values or Terraform state are committed. Example inputs are clearly placeholders.

## 3. Desired-state coverage

| Domain | Required convergence and observation |
| --- | --- |
| Host | Package dependencies (Podman/Quadlet, Node, flock, age and backup tooling), service identity, subuid/subgid, lingering, rootless systemd, cgroup and available disk; no broad OS upgrade or unrelated firewall changes. |
| Storage/network | Install canonical network and volume Quadlets, preserve exact existing volume names and data, validate private DB network, permissions, mount semantics and absence of public API/DB ports. Never delete/recreate a data volume to resolve drift. |
| Secrets | Create missing Podman secrets from protected inputs, verify existing values without disclosure, fail closed on mismatch. Explicit coordinated rotation is separate from routine convergence; no implicit DB or signing-key rotation. |
| PostgreSQL | Install pinned DB unit and init script before initial startup; adopt existing DB by verifying identity/roles and schema. Initialize only empty/new storage; never rerun first-install SQL against a live database. Maintain distinct writer/admin/preflight credentials and least-privileged preflight grants. DB image/schema changes require explicit maintenance. |
| Tunnel | Install a complete pinned connector Quadlet with only loopback metrics binding, declared secret and expected proxy dependency. Verify connector readiness; do not rewrite a live route until the corresponding private proxy is verified. |
| Runtime | Validate and apply profile, browser auth, resource and model-cache configuration through a shared typed host contract consumed by the existing updater. Legacy and slot settings must agree with the declared supported runtime; unknown legacy deviations block cutover rather than disappear silently. |

## 4. Lifecycle contract

The existing `site.yml` remains the Ansible entrypoint. Implementation may split its tasks into roles or includes; avoid two competing playbooks for the same configuration. Define and document concrete stage names, inputs, output evidence, restart impact and dependencies as they are implemented. The final interface must provide these operations:

1. **Inspect/plan:** read-only inventory and drift report; no application writes or restarts. Unknown topology or unobservable prerequisites fail closed.
2. **Converge base:** prepare an empty SSH-ready VM or adopt an existing one; establish host, secrets, storage/network, database and declared static units without changing a running writer unexpectedly. A second run against matching desired state is unchanged.
3. **Bootstrap/adopt:** distinguish empty install, legacy serving writer, and initialized controller. Verify authenticated signed channel, certified artifact, real frontend identity, backup evidence and DB compatibility before disruption. Handle a legacy API that does not yet advertise an epoch by an explicit compatible bootstrap release transition, not by guessing an epoch or bypassing preflight. A fresh install may initialize DB schema using the existing migration authority once, before updater read-only preflight. No unsigned release or second writer. If the real UI identity is not available/compatible, a coordinated initial deployment must establish the identity contract without weakening normal production gates.
4. **Cutover/acceptance:** preserve the former writer/configuration, fence old writer, initialize controller and prove private proxy readiness, then hand off to the separately reviewed Terraform origin change. Verify routed identity and persistence, anonymous and out-of-scope denial, reboot and update/rollback. Record evidence. Enable polling only after acceptance.
5. **Steady-state converge:** detect and safely repair declared drift after initialization, including controller source/config, units and credentials as appropriate. Routine converge is non-disruptive; runtime/DB changes requiring interruption must be planned and explicitly approved. Respect updater lock and preserve paused/disabled state when intended. No silent changes to release selection, key trust or journal.
6. **Maintenance/recovery:** explicit pause, resume, backup, restore drill, compatible rollback, controlled controller/credential/DB or incompatible epoch transition. Resume the original writer on recoverable failure using the canonical controller; if ownership or compatibility cannot be proven remain blocked and preserve evidence. Reconcile interrupted first adoption, including failure before a journal exists. Do not delete the journal or suppress a failed digest to retry.
7. **Verify:** read-only host and externally routed checks; verify the actually running release, not merely installed files, and distinguish configured, deployed and accepted.

A private Terraform plan/application and publisher provisioning are explicit dependencies, not VM shell tasks. The initial signed channel must be bootstrapped by the protected publisher and advertise a certified release; Ansible only verifies/consumes that trust. Do not introduce CI-to-VM credentials to work around bootstrap. The present legacy origin and missing channel must be resolved through these established authority boundaries.

## 5. Security and failure invariants

- Preserve PostgreSQL and history volumes, existing author data, browser recovery semantics and rootless network isolation. Keep the single-writer invariant across Ansible, updater, backup, reboot and interruption.
- The updater owns host-level locking and writer/route state. Any operation touching those resources must use a compatible locked maintenance interface; do not acquire the same non-reentrant lock and call a second lock-taking process.
- Routine runs must not stop a working service, rotate a credential or downgrade a release as a side effect of file reconciliation. Unsafe drift is reported, not blindly overwritten. Before starting a slot, require absence of stopped/running slot and preflight containers, and verify the generated systemd fragment and reviewed Quadlet source. Normal preflight cleanup requires the journal-selected image and controller ownership label, checks the observed image and mounts, and removes only the observed container ID without removing volumes. Approval never overrides integrity, compatibility or backup verification.
- Secrets use protected files/Vault/external secret inputs, restrictive permissions and no-log/no-diff paths; no credentials in stdout, facts/artifacts, shell arguments, public repo or GitHub Actions VM inputs.
- Artifacts are digest-pinned; verify profile, source, schema fingerprint, API/persistence epochs and signed-channel membership where applicable. Keep existing Access, CSRF, auth and exact-source CI gates.
- Failed adoption must be retryable from observed durable state. Do not manually start slot units or delete state, data, secrets or unrelated host resources as a recovery mechanism.

## 6. Implementation and proof gates

Implement in dependency order using independent Issues and reviewable PRs. The existing tasks and controllers are reused rather than rewritten. The migration is complete only when all lifecycle operations are covered and a real target-host acceptance record exists.

| Phase | Deliverable | Required evidence |
| --- | --- | --- |
| A | Inventory, read-only host inspection, host/account/toolchain convergence | Schema rejection before mutation; matching host second run unchanged; supported rootless systemd/Quadlet on Ubuntu target |
| B | Base networks, volumes, secrets, PostgreSQL, static Tunnel unit | Fresh disposable host convergence, existing-data adoption, second run unchanged, secret mismatch/write denial, no public DB/API binding |
| C | Shared runtime contract and controlled updater lifecycle | Core/Full settings retained across slots and reboot, pinned images, post-init drift verification, controlled source/unit/config update and failure handling |
| D | Legacy/empty bootstrap and cutover | Signed channel admission, old epoch bootstrap, migration ledger and backup proof, no overlapping writers, interruptions before/after journal, proxy/Access compatibility and rollback |
| E | Backup and maintenance lifecycle | Real encrypted remote backup, isolated restore, interruption and failed restore behavior, no live overwrite, recovery/credential/migration operations |
| F | End-to-end integration and operational acceptance | Real Ubuntu VM fresh/repeated apply, existing deployment adoption, reboot, signed update/rollback, Full model workload, external identity/denial and authenticated author smoke test; measured backup/restore and no untracked host drift |

CI must syntax-check and exercise the actual roles, use disposable PostgreSQL and an isolated real rootless Podman/systemd VM for integration proofs (not solely a mocked Podman command). Run fresh converge, repeat, deliberate drift, interrupted operations and recovery. Tests may separate expensive VM proof from PR fast checks, but missing external evidence is NOT_CHECKED, not success. Production application requires explicit authorization and verified recovery evidence. Preserve current exact-source release certification and independent UI/backend release lanes.

## Inputs and trust

Use a reviewed checkout of this repository and an SSH inventory with host-key verification. The host must already have Podman/Quadlet, Node.js 22+, flock and systemd user services with lingering. For an existing deployment, PostgreSQL data, canonical volume/network identities and Tunnel credentials remain operator-owned inputs for safe adoption. The explicit `secrets` and `base` stages run through a separate bootstrap account with Ansible privilege escalation; Ansible runs rootless Podman/systemd operations as the existing service account, which receives no sudo grant. The updater-only `prepare`, `initialize`, `enable`, and `verify` stages continue to use the existing rootless service identity. The privileged `base` stage provisions `/opt/codexia-updater` when absent; `prepare` requires the existing service-owned mode-0750 directory and does not request sudo. The explicit `secrets` and `base` stages can create missing fixed resources on a fresh host; they never replace existing identities or initialize a nonempty or unknown database layout. VM creation, base OS installation, initial PostgreSQL data restore and private Terraform state are operator infrastructure prerequisites.

Install the version pinned in `deploy/ansible/requirements.txt` in an isolated control-node environment (Python 3.12–3.14 for Ansible Core 2.21). Copy `deploy/ansible/inventory.example.yml` to a private location; supply real host, Full/Core-compatible public origin, independently trusted signing public key, immutable certified proxy digest and explicit current browserAuth. Supply GitHub repository read and paired Access service credentials as private control-node files; use Ansible Vault or an external secret manager for `codexia_preflight_password` (independent 32-byte hexadecimal secret). Never commit inventory credentials, private files, Terraform state or installed-release records. Existing credentials are not rotated implicitly. The control node and the target service account are trusted; do not run with verbose secret logging.

## Base secrets and static resources

Run the `secrets` stage through the bootstrap account before `base`. Ansible adopts matching credentials or creates missing credentials only when no canonical data or application containers exist; a mismatch or missing credential on an existing runtime fails closed. See [`BASE-SECRETS.md`](../../deploy/ansible/BASE-SECRETS.md) for protected input requirements.

The `base` stage validates all existing Quadlet sources, volume/network identities, PostgreSQL data and any existing Tunnel container before creating files or Podman resources. It installs only missing fixed network, volume, database and Tunnel definitions; it does not overwrite drift, restart an existing database or start the Tunnel. Existing Tunnel adoption checks the pinned image, exact private network, loopback-only metrics port, protected token mount and read-only root filesystem. An empty or absent PostgreSQL volume requires the separate `codexia_database_initialization_approved=true` attestation. A missing application role is recoverable only on an explicitly approved empty database using the existing app secret; it never changes an existing password. Adopted PostgreSQL clusters must be version 17, have the required control files, and match the packaged migration ledger when that ledger exists. The base stage does not run schema migrations. For a fresh host, the separately approved `initialize-schema` stage after prepare uses the signed release's fresh-only migration authority under the host lock, without an API writer; it rejects untracked objects and partial ledgers, records a durable pristine-database intent bound to the release and actual database identity before migration, then converges read-only preflight grants. An exact ledger without that intent is not proof of a fresh installation. This does not activate a writer or complete Phase D. The subsequent explicit `initialize-fresh` stage requires the durable matching schema receipt and starts the private proxy and exclusive writer under the controller lock; the durable first-activation marker recovers interruptions. It leaves the Tunnel stopped and public handoff/polling disabled. See [`BASE-RUNTIME.md`](../../deploy/ansible/BASE-RUNTIME.md) for the commands and exact behavior.

## Converge

The encrypted backup helper also exposes a push-maintenance adapter for use by a separately reviewed transaction that owns a durable host lock. After that transaction has blocked admission and stopped every writer, it can pass the open lock file descriptor directly to the helper:

```sh
exec 9<> /run/user/1000/codexia-maintenance/host.lock
flock --exclusive --nonblock 9
deploy/updater/standalone-backup.sh backup-locked /private/off-vm-mount "$CODEXIA_BACKUP_RECIPIENT" \
  --approved --lock-file /run/user/1000/codexia-maintenance/host.lock --lock-fd 9
```

The caller must create and exclusively hold the existing lock before invoking the command, keep the descriptor open through backup completion, and restore the prior service/route state through its own durable recovery transaction. The helper rejects an absent or symbolic-link lock file, a descriptor for a different inode, an unheld descriptor, a local backup destination, and a missing explicit approval. This interface shares the existing encrypted artifact and fingerprint implementation; it does not stop writers, fence traffic, recover interrupted deployment, or replace the current updater-backed Ansible backup stage. Keep the backup and isolated restore evidence bound to the deployment before any push rollout that can change persistent data.

From the repository root, run the following with a private inventory and an encrypted extra-vars file:

```sh
ansible-playbook -i /private/codexia-inventory.yml deploy/ansible/site.yml \
  -e @/private/codexia-vault.yml --ask-vault-pass -e codexia_stage=prepare
```

`prepare` verifies the existing host topology; installs the canonical updater runtime, disabled configuration, private credentials and blocked route; converges the preflight role and secret; and installs the private proxy Quadlet without starting or stopping a writer. The SQL refuses unsafe existing roles rather than silently revoking unknown privileges. A second execution does not recreate the role or secret, rotate passwords or restart services. A check-mode run is useful for file differences but does not execute database convergence or prove runtime acceptance.

For first activation, obtain the exact matching source backup and isolated restore receipt described in [Standalone backup](STANDALONE-BACKUP.md#legacy-cutover-backup-evidence); supply the private `codexia_restore_receipt_file`. The pre-drain gate revalidates the remote artifact. Then review the legacy writer configuration, including custom mounts/runtime settings (the current controller supports only its canonical slot configuration). Confirm the installed release is signed and compatible with the real frontend; provide its exact release record as `codexia_installed_release_file`. During the approved maintenance window, run the same playbook with `-e codexia_stage=initialize -e codexia_maintenance_approved=true`. It provisions reviewed boot recovery before disruption and performs the same-release adoption transaction. Pre-journal interruption restores the captured legacy sources and uses identity-preserving backup recovery; post-journal interruption resumes only the journal-owned writer before completing Tunnel handoff. No polling is enabled.

For an old-epoch legacy API, first run `bootstrap-preflight` after `prepare` with `codexia_installed_release_file` and `codexia_bootstrap_candidate_file`. The candidate must be a separately signed forward release with the same schema, persistence format, profile and platform, and its API epoch must match the real deployed UI. The stage verifies read-only candidate readiness while the legacy writer serves. After verifying a matching off-VM backup and isolated restore receipt, run `-e codexia_stage=bootstrap-cutover -e codexia_maintenance_approved=true` with the same release files. This distinct transaction stores backup identity against the legacy release and activation identity against the candidate, then rechecks source/runtime identity, channel membership and backup evidence immediately before stopping the legacy writer. Before the candidate journal is durable, recovery restores the legacy configuration; after it is durable, recovery can resume only the candidate with the route blocked until writer probes pass. Existing v1 same-release recovery intents remain supported. Unknown source or runtime identity remains blocked with durable evidence; never delete state to retry. Neither bootstrap stage enables polling or constitutes production acceptance.

Apply the reviewed Terraform plan with `origin_service = "http://codexia-api-proxy:3000"` using the existing private state; preserve Access and routes. Ansible does not apply Terraform or change Cloudflare access policy. Execute the [target-VM acceptance](STANDALONE-UPDATER.md#acceptance-target-vm-required), including backup/restore, fault/reboot and rollback exercises. For the real update/rollback exercise, keep the timer inactive and the initialized controller disabled and paused. Provide a second forward-compatible published release in the signed channel. Run the playbook with `-e codexia_stage=acceptance-update -e codexia_maintenance_approved=true`, verify the committed candidate, then `-e codexia_stage=acceptance-rollback -e codexia_maintenance_approved=true`. Both commands use the existing locked admission and rollback path, require a real release transition and preserve the paused state; rollback suppresses the exercised digest just as normal rollback does. A missing candidate or previous release fails the exercise. Only after success, run `-e codexia_stage=enable -e codexia_acceptance_approved=true`. It checks controller topology and real public API identity, enables the config, resumes the controller and starts the timer. An approved rerun may complete the forward-only interruption after the enabled configuration was written: it accepts only disabled/inactive, enabled/inactive or enabled/active timer state, then verifies the timer is active and enabled after convergence. Other timer drift still fails closed. The approval variables are explicit operator attestations, not proof of backup or acceptance.

Run `-e codexia_stage=verify` to inspect initialized topology, probe the live private proxy and authenticated persistence, and verify existing preflight role grants and secret without mutating them. For an approved `resume`, a read-only locked check also accepts the exact `Interrupted update recovered from durable journal` error only when the journal is stable, the backup recovery gate is clear, and the canonical writer units, route and serving probes pass. It preserves the pre-interruption pause and timer state. Resume then clears that error through the normal locked controller command; unrelated errors or uncertain ownership remain blocked. After initialization, prepare/initialize are read-only verification, not a second bootstrap. Controller runtime upgrades and credential rotation require separate maintenance: stop polling, reconcile state, review the source/config change and verify before resuming. No playbook operation deletes application data or replaces database/volume identities. Do not run simultaneous Ansible invocations against the same VM; the updater owns its own host lock.

For an initialized controller, stage a reviewed checkout and run `ansible-playbook -i /private/codexia-inventory.yml deploy/ansible/site.yml -e @/private/codexia-vault.yml --ask-vault-pass -e codexia_stage=maintain -e codexia_maintenance_approved=true`. The task stages source, configuration, units and proxy input under the private state directory, then applies them through the existing updater lock. It suspends polling and preserves the journal, route and prior pause state. Runtime changes fence and restart only the active slot writer; proxy changes fence traffic while the proxy restarts. It verifies the resulting writer, proxy, unit and source state before restoring the prior timer state. On failure it restores the recorded files and prior runtime; if ownership or recovery cannot be proven, it leaves traffic blocked, the controller paused and polling stopped, with the recovery marker retained for operator repair. Review the emitted `codexia-updater-maintenance/v1` result and run `verify` before closing the maintenance window. This stage requires an initialized journal and does not handle first adoption.

For GitHub channel-read and Cloudflare Access probe credential rotation, first install the reviewed maintenance runtime through `maintain`. Supply the three replacement private files in the usual inventory and run `-e codexia_stage=rotate-probe-credentials -e codexia_probe_credential_rotation_approved=true`. The old credentials must remain valid until success. The credential-only transaction verifies both the old and staged inputs against the signed channel/checkpoint, actual frontend and backend identities and the canonical exact-path Access boundary (anonymous identity and credentialed author route denial), snapshots the old values privately, suspends polling, atomically installs the canonical credential files, verifies the new credentials and scoped live Access again, then restores prior pause/timer state. An interrupted or failed operation restores the old files using the existing durable transaction. Boot recovery verifies the exact committed writer configuration and starts only the recorded slot if it is absent; an existing foreign writer, unknown stopped container, or preflight blocks recovery. It never resumes polling if the original credential scope or serving state cannot be verified. No writer, database, signing key, browser-auth configuration, Podman secret or proxy image is changed. Revoke old credentials only after success. PostgreSQL DB and incompatible schema/epoch maintenance remain separate from this stage.

PostgreSQL app-password rotation is a separate, explicitly disruptive maintenance stage. First install the reviewed updater and verify a current off-VM backup and isolated restore receipt bound to the same installed release, journal generation and PostgreSQL database identity. Supply `codexia_postgres_app_password_rotation_file` and `codexia_app_password_restore_receipt_file` as private control-node files, then run `-e codexia_stage=rotate-app-password -e codexia_app_password_rotation_approved=true`. The transaction runs under the existing host lock. It stops polling, pauses the controller and blocks route admission, changes the PostgreSQL `codexia` role through stdin-only SQL, replaces the immutable canonical Podman secret, and restarts the exact reviewed database and journal-owned writer without replacing persistent volumes. A temporary private API outage is expected. The operation restores the prior route and timer only after checking the same database identity, successful new app authentication and committed writer. Recovery after interruption restores the old SQL password and secret; if identity or serving state is ambiguous it retains the recovery marker, keeps the route blocked and polling stopped, and requires operator repair. Keep the old credential valid until success. Run `verify` and complete the disposable rootless PostgreSQL/systemd crash-recovery exercise before production use; the implementation alone does not constitute live acceptance.

Tunnel-token rotation is a separate explicitly approved local-secret operation. Create the replacement with the external Cloudflare secret authority, keep the prior token valid, update the protected `codexia_tunnel_token_file`, then run `-e codexia_stage=rotate-tunnel-token -e codexia_tunnel_token_rotation_approved=true`. Under the updater lock, the stage verifies the exact reviewed Tunnel Quadlet, running container and mounted secret, then records a durable rollback marker, pauses polling, replaces only the immutable `codexia-tunnel-token` secret and restarts the Tunnel service. It verifies the same Tunnel runtime, committed writer and route before restoring the prior timer state. Interrupted recovery restores the captured old secret and service; if the source, secret or runtime cannot be proven it leaves polling stopped and retains the marker. The stage does not contact Cloudflare or verify remote connectivity. Use normal public-service acceptance to verify the new Tunnel before revoking the prior token. Complete the disposable rootless secret/service interruption test before production use.

Standalone API token rotation is a separate, explicitly disruptive credential stage. Pause the controller and install the reviewed updater first. Supply `codexia_api_auth_token_rotation_file` as a private control-node file, then run `-e codexia_stage=rotate-api-auth-token -e codexia_api_auth_token_rotation_approved=true`. Under the existing updater lock, the transaction snapshots both credentials durably, stops polling, blocks route admission and restarts only the journal-owned writer with the new immutable `codexia-auth-token` secret. While the route is blocked, it requires the new bearer token to authenticate and the prior token to return `401`; only then does it restore the route and verify routed service readiness. An applying marker recovers by restoring the old token and writer. A durable completed marker recovers forward using the replacement token. An unprovable secret, writer, route or auth result keeps the route blocked and polling stopped. This stage requires the controller to be paused before invocation; API restart invalidates in-memory cookie sessions, and success revokes old bearer/login tokens, so prepare all clients to use the replacement. Complete the disposable rootless Podman/systemd interruption and boot-recovery exercise before production use. The implementation is not live acceptance.

## PostgreSQL preflight-password rotation

PostgreSQL preflight-password rotation separately changes the `codexia_preflight` read-only setup role and its canonical `codexia-postgres-preflight-password` secret. Verify an off-VM backup and isolated restore receipt for the exact controller generation and database identity, provide `codexia_postgres_preflight_password_rotation_file` and `codexia_preflight_password_restore_receipt_file` as private control-node files, then run `-e codexia_stage=rotate-preflight-password -e codexia_preflight_password_rotation_approved=true`. The transaction uses the existing host lock, stops polling, blocks the route, and stops the committed writer. It changes only the preflight role password and immutable secret used by temporary read-only preflight containers. PostgreSQL stays running while the operation verifies the new credential, restarts the committed writer and restores the API route.

After an interruption, check the rotation phase in `maintenance/in-progress.json` alongside the controller state file. With `applying`, recovery restores the previous SQL password and Podman secret from the durable snapshot. With `rolled-back`, it verifies the previous credential against the recorded digest. With `completed`, it verifies the replacement credential against the recorded digest and finishes the rotation. Keep both credentials available until recovery finishes and use the credential corresponding to the resulting phase for the subsequent Ansible `verify`. The controller verifies the same database and committed writer before restoring the recorded route and timer. An unverified identity or recovery state retains the marker with route admission and polling blocked. Complete the disposable rootless PostgreSQL interruption test before production use.
