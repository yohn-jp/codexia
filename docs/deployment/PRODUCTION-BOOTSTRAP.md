# Protected production Bootstrap workflow

Use this runbook to provision a VM, enroll its first owner through the normal frontend and activate the certified Backend. [Initial deployment](INITIAL-DEPLOYMENT-FLOW.md) owns the input and recovery contract. [Deployment lifecycle](DEPLOYMENT-LIFECYCLE.md) owns route selection. The management path is GitHub Actions → Tailscale OIDC → pinned SSH → Ansible → rootless Podman Quadlet.

## Establish access and recovery custody

Use protected GitHub Environments with required reviewers and deployment restricted to main. The VM must be reachable over the tailnet and the independent administrator must have noninteractive sudo. Obtain the VM's SSH host key through the provider console or an independently authenticated channel. Provision the administrator's public SSH key on that account. Provision a separate deployment identity for the rootless service. R4 derives its public half inside the runtime Environment, installs it on the target, and verifies a real runtime login against the same VM identity.

The controller builds a single-host Ansible inventory in a private runner directory. R4 receives the external Tunnel credential individually. On a fresh target the VM generates the PostgreSQL admin, application and auth-role passwords, Better Auth secret and OAuth introspection secret. On an existing target, the VM checks its existing identities and values. Missing credentials with existing data, a different Tunnel token, a UID conflict or an unverified DB state require reconciliation before proceeding.

## Read-only lifecycle preflight

1. Run [Production Bootstrap](../../.github/workflows/production-bootstrap.yml) with `mode=preflight` to check the pinned administrator login, sudo and generated inventory. This connection test takes no DB passwords, Tunnel token, recovery credentials or release identifiers.
2. Open [Production Access Preflight](../../.github/workflows/production-preflight.yml) on main. Select `mode=lifecycle`, an intent and the management identity. Select `bootstrap` for R4 and the two R5 owner operations, and `runtime` for initial frontend publication and R6. For R6 supply the approved UTC window via `window_start` and `window_end`. When observing an existing writer, the prior publisher reference can identify its installed certificate.
3. Review the candidate route, target, blockers, required approvals and window in the redacted plan. Preflight resolves the certified Backend and compatible Full frontend from CI evidence. A plan whose only blocker is approval can be reviewed. Missing evidence or unresolved source identity stops the operation.
4. Pass that successful Preflight's run ID as `preflight_run_id` to the owning workflow. The workflow retrieves attempt 1 from the same repository, main SHA and management identity, recertifies the candidate and repeats the live observations in the production queue. After state changes or a rerun, start a new Preflight dispatch and review its new ID.

## Publishing the normal frontend for first-owner enrollment

The normal Full frontend contains the Desktop `/console/setup` route. Provision the canonical Worker and routes under the existing Cloudflare infrastructure approval, using `manage_frontend_worker=true` when absent and `frontend_route_enabled=true`. Keep the public OAuth/MCP bypass disabled until normal runtime acceptance. The protected R5 publication verifies the archive and canonical Access routes, checks the monotonic frontend identity and reconciles its immutable release record. A retry after an interrupted upload or record write requires fresh observation. The same Worker serves the owner after activation.

## Interrupted installations and recovery

A positively absent logical DB can be initialized with install intent and explicit DB approval. The controller rechecks absence and the installation checkpoint under the host lock before touching DB-bound deployment state. A matching cluster ID, database OID, current ledger and certified image allow the documented Auth-only continuation. Restore intent routes to recovery. Existing owner identity, Passkey and registered clients must survive adoption or restoration.

If an existing VM already has an intact set of credentials and is waiting for owner setup (R5) or first activation (R6), obtain an administrator Preflight with install intent. Run [Bootstrap credential recovery](../../.github/workflows/bootstrap-recovery.yml) with `mode=adopt` and that `preflight-run`. The job checks the observed DB, owner state, transaction and Podman IDs under the existing lock, then encrypts and independently recovers those same credentials. An R6 plan blocked solely on preservation, window and approval evidence can authorize this credential capture. Backend activation still requires a successful runtime Preflight with all its evidence.

If the grant expired or its encrypted handoff was lost, use the [separately approved owner reissue procedure](../../deploy/ansible/AUTH-RUNTIME.md#first-owner-through-the-browser). If a credential drill failed, verify the original R4 receipt using [Bootstrap credential recovery](../../.github/workflows/bootstrap-recovery.yml) with its producing run and attempt. If the enrolled database was prepared but its independent data drill failed or expired, dispatch [Verify first activation recovery point](../../.github/workflows/initial-preservation.yml) on current main and repeat the runtime Preflight. Reissuing an owner grant is unnecessary for a prepared owner.
