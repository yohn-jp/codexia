# Standalone automatic updates (O2/O3)
 
The rootless host controller is opt-in. It is not a database migration tool and is not used for Hosted. It requires the signed stable channel, embedded backend identity, migration fingerprint, and deployed frontend identity contracts. Do not activate before those dependencies have converged and the target VM acceptance has passed.
 
## Topology and bootstrap
 
- Install the verified source tree under /opt/codexia-updater, owned by the deployment operator, with Node.js 22+, Podman/Quadlet, systemd user services, and flock.
- Retain the existing codexia-db service, codexia and codexia-data networks, and codexia-data/history volumes. Provision codexia_preflight using deploy/updater/provision-preflight-role.sql as a dedicated non-owner reader. Set its password via a protected psql variable, and create the Podman secret codexia-postgres-preflight-password. Never reuse the application writer password or expose the preflight role externally. Verify read-only privileges and that it cannot write persistent canon tables.
- Use ~/.local/state/codexia-updater for the route and controller journal (mode 0700); initially create route with the text blocked. Copy config.example.json to ~/.config/codexia-updater/config.json; adjust absolute paths and the HTTPS desktop identity URL. Pin the trusted signing public key independently. Store a repository read credential and paired Cloudflare Access service credentials in private files, not the journal. Keep enabled=false.
- Install codexia-api-proxy.container.example as a Quadlet, substitute a verified immutable image digest, and retain the private network only (no published port). Stop and disable the legacy codexia-api writer and remove its Quadlet from the generator directory before activating slots. Keep a backup of the legacy configuration. Change the existing Tunnel origin once to http://codexia-api-proxy:3000, and remove any legacy API service dependency from its unit. Cloudflare Access remains the external ingress.
- Reload user systemd, start the database and proxy, then use the locked wrapper: sh /opt/codexia-updater/deploy/updater/codexia-updater init /absolute/config.json /absolute/installed-release.json. The installed-release document must match a published entry in the authenticated channel. Initialization refuses a running legacy or slot writer. The writer is started only after isolated preflight and real schema verification.
- Install the boot and poll service/timer examples under ~/.config/systemd/user. The boot unit restores the journaled writer before timer activity. The slot Quadlets have no independent boot install target. Never start slot writers manually. Enable the timer only after acceptance and explicit operator enablement, then resume the journal. The wrapper uses a host-wide kernel flock for all commands.
 
## Update and recovery contract
 
Every poll validates freshness and signature, persists the checkpoint, selects a compatible immutable release, verifies the pulled artifact and packaged schema, and runs isolated preflight with no shared writable volumes or writer credential. The actual frontend identity and signed channel are rechecked before stopping the old writer. Admission is blocked before old-writer shutdown; no new writer starts until the old writer is stopped and absence of writers is observed. The proxy is switched only after the new writer is ready. Health, routed version and authenticated persistence probes run during observation. An unhealthy candidate is fenced before restoration. An unexpected topology blocks traffic and pauses rather than guessing. A successful boot can use a locally cached verified installed artifact.
 
Commands: status, pause, resume, tick, boot, rollback. Explicit rollback requires an authenticated, still-published compatible previous release. The same exclusive cutover is used; failed digests are suppressed. Failed or interrupted transitions reconcile to the prior recorded writer, or stay blocked if exclusive ownership cannot be established. A major/schema-changing upgrade remains an operator-controlled maintenance procedure.
 
## Acceptance (target VM required)
 
Exercise candidate preflight failure, stale/withdrawn channel, incompatible schema and frontend, concurrent poll rejection, crash before/after stopping the old writer, failed readiness, explicit rollback, reboot during cutover, and proxy streaming. Confirm Podman ownership, read-only preflight grants, database ledger unchanged, history persistence, authentication and Access/Tunnel route on the actual VM. Record observations and outage duration. This repository includes host orchestration tests, not evidence of a live VM deployment.
