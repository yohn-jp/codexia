# Standalone backup and isolated restore drill

The backup controller command holds the same host-wide `flock` as updater operations. It is available for both a pre-journal legacy writer and a stable initialized controller. The existing `site.yml` exposes `backup` and `restore-drill` stages; the restore drill delegates its work to the local recovery host before running any source-VM service checks.

The age recipient and off-VM destination are external inputs. Supply them through a protected inventory or Vault and keep Ansible `no_log` enabled. Provision the recipient and recovery identity independently; this workflow never creates or rotates production backup credentials. Keep the private recovery key on an isolated recovery host, never on the source VM or alongside the artifact. The remote destination must be independently protected against deletion and modification and have a retention policy.

## Encrypted backup

Run the rootless `codexia-updater` wrapper with one of these forms:

```sh
codexia-updater backup /absolute/config.json /absolute/remote/mount age1-public-recipient --approved
codexia-updater backup /absolute/config.json /absolute/signed-legacy-release.json /absolute/remote/mount age1-public-recipient --approved
```

The first form requires a valid stable controller journal, one verified serving slot writer, the route targeting that writer, and no preflight containers. The second form requires no controller journal, an exact legacy release record published in the signed channel, a matching running legacy image/version/profile/browser-auth identity, a blocked controller-owned route marker, and zero slot or preflight writers. For the backup identity check only, the legacy `/api/version` response may omit `apiEpoch`; if present, it must match the signed release. This exception does not change the strict epoch checks used by `verify-legacy`, initialization or cutover.

The controller validates the external mount before stopping any service. For a legacy backup, a private durable recovery marker binds API and Tunnel Quadlet/generated-unit sources, pinned image identities, complete sanitized Podman `Config` and `HostConfig`, network IDs, declared secret IDs and targets, and the exact generated `default.target.wants` link state. The runtime fingerprint preserves argument and environment order, rejects plaintext secret environment values and hashes only validated secret mount options from `Config.CreateCommand`; it omits the hostname Podman derives from the container ID. The recovery marker is atomically written and synchronized before the startup fences are installed; the primary intent and recovery marker must match whenever both exist. Quadlet owns the generated `WantedBy` links, so the controller records and verifies them without calling `systemctl enable` or `disable`. The persistent fence allows a start only when the recovery marker is absent or that unit's one-use permit exists. The permit link resolves through an open descriptor in the controller process, so it stops authorizing starts if the process exits unexpectedly. The controller blocks admission through the existing route adapter and stops the active writer and (for legacy) Tunnel connector. Quadlet may remove a stopped container; recovery recreates it only after its source identity still matches the intent, then compares its complete sanitized runtime configuration before continuing. Each recovery permit is created only after identity checks, used for one service start under the controller lock, and removed before the next service can start. The independent recovery marker remains until the primary intent is durably cleared. The controller restores the primary intent after an uncertain primary clear when possible; if that write also fails, the recovery marker still carries the validated recovery record. Unknown identity or multiple writers leave ingress blocked and preserve recovery evidence. Once API and Tunnel identities, timer state, and the unchanged generated links are verified, the primary intent and then the recovery marker are durably cleared while both startup fences remain installed; the fences are removed last. If either intent clear reports an error, the controller blocks the route, stops polling, re-saves the affected recovery record when possible, and retains the recognized fence files. After the recovery marker is gone, service restoration has already been fully verified, so ordinary autostart is safe even if fence cleanup is interrupted; a later no-intent pass removes any remaining recognized drop-ins. The existing encrypted backup code runs while the controller retains the host lock. The wrapper passes its open lock descriptor to the controller; the backup helper verifies that inherited descriptor identifies the canonical lock and remains locked, without opening a nested lock. It rejects a helper process that only observes another process holding that lock. The controller restores the prior Tunnel/timer state and preserves the journal and paused state. It never writes a Cloudflare route or changes DB schema or credentials. A failure that cannot be recovered leaves admission blocked and retains evidence; it does not create a controller journal.

Install updated updater source and configuration with the read-only `prepare` stage before invoking `backup`. Then run `site.yml` with `codexia_stage=backup`, `codexia_backup_approved=true`, the destination and public age recipient from protected inputs, and the exact signed installed-release file when the controller journal does not yet exist. The stage invokes the mode-0600 wrapper through `sh` and enables the existing boot recovery unit before the maintenance window. A successful legacy backup command confirms both artifact publication and the identity-checked recovery under the same lock; it does not run the strict cutover-only `verify-legacy` check afterward. It does not start that unit or enable polling as part of the backup operation.

The destination must be an existing absolute NFS, CIFS or SSHFS mount whose source host resolves to an address that is not assigned to this VM. This rejects loopback and same-VM mounts; it does not prove the remote storage's ownership, immutability or custody. The database custom-format dump and history-volume archive stream directly into age ciphertext. The encrypted manifest stores logical fingerprints of public PostgreSQL table rows and history file names/content; the artifact directory records SHA-256 checksums. These checksums detect corruption but do not authenticate who created an artifact: the age recipient is public, so anyone can encrypt a fabricated artifact to it. Production recovery evidence therefore also requires independently verified write protection or a signed storage receipt before the artifact is treated as an authentic backup. A partial directory is published only after all ciphertext and checksums have been synchronized. The backup database image pin matches the deployed PostgreSQL 17 Quadlet pin.

## Initialized controller backup evidence

After successful backup and verified writer recovery, the locked source updater records `controller-backup-proof.json` in its private state directory. The record binds the exact installed release, controller journal generation, PostgreSQL system/database identity, off-VM artifact directory and ciphertext manifest SHA-256. It is recorded only after checking the published artifact again; the database identity and journal must remain unchanged throughout backup and recovery. Existing backup output is unchanged. The latest successful initialized backup provides the selected source evidence.

Use the existing isolated restore drill to obtain the matching private restore receipt. The locked internal `verify-maintenance-backup /absolute/config.json /absolute/private/restore-receipt.json` command revalidates the current artifact, exact installed release, generation, database identity, receipt and serving writer without changing state. This is backup evidence, not authorization to mutate the database: a disruptive maintenance operation must recheck the evidence within its own lock and establish its required recovery point. It does not prove that no author data changed since backup or that production recovery was accepted.

## Legacy cutover backup evidence

After a successful controller-locked legacy backup and identity-preserving recovery, the source updater records a private `legacy-backup-proof.json` in its existing state directory, binding the exact signed legacy release to the committed off-VM artifact path and SHA-256 of its fixed ciphertext manifest. Only the latest successful source proof is selected. Backups produced before this proof exists must be repeated.

The isolated drill verifies the same manifest before and after restoration and emits its SHA-256 only after successful fingerprint comparison and scratch cleanup. Set `codexia_restore_receipt_output_file=/private/new-restore-receipt.json` on the isolated recovery host. Transfer that private receipt to the trusted Ansible control node and pass `codexia_restore_receipt_file=/private/new-restore-receipt.json` to legacy initialization. The receipt is an operator-protected recovery-host record, not a cryptographic attestation of host identity. The source updater rechecks the off-VM mount, every ciphertext checksum, the exact legacy release and receipt binding before writer disruption. Missing or different proof blocks initialization. This does not prove zero RPO or full production acceptance.

## Isolated restore drill

Run the drill on an isolated recovery host with Podman and the external recovery identity:

```sh
bash deploy/updater/standalone-backup.sh drill \
  /absolute/remote/backup/directory /absolute/private/age-identity --approved
```

The same operation is available through `site.yml` as an explicitly selected local recovery stage. Run it on the isolated recovery host, with the approval, mounted backup directory and recovery identity path supplied through protected local inputs:

```sh
ansible-playbook -i localhost, -c local deploy/ansible/site.yml \
  -e @/private/recovery-inputs.yml --ask-vault-pass \
  -e codexia_stage=restore-drill -e codexia_restore_drill_approved=true
```

Pass `codexia_stage=restore-drill` explicitly as an extra variable: the dispatcher selects localhost before gathering any source-VM facts, does not require the source VM or its inventory, and runs the recovery tasks only once. Check mode and a source-host-selected recovery stage are rejected rather than reported as restore evidence.

The directory must resolve to an approved remote filesystem whose source host is not this recovery VM. The recovery identity must be a regular non-symlink file owned by the recovery user with mode `0400` or `0600`. The script verifies fixed ciphertext checksums and decrypts the manifest before creating scratch resources. It restores into uniquely named, labeled PostgreSQL and history volumes with no network and no published ports, then compares the restored logical fingerprints. Cleanup removes only resources with the exact generated drill label, verifies every scratch object is absent, and returns failure if a removal or absence check fails. The success message is printed only after cleanup succeeds; the exit trap retries cleanup after an interrupted or failed removal. It cannot select or restore into production volume names. The Ansible restore-drill include delegates to the local recovery host and checks the private-key path and mode without reading the key contents.

The drill does not restore production role passwords, grants, Cloudflare credentials, systemd configuration or browser-local drafts. The database fingerprint covers row values, not physical WAL, sequence state, ACLs or server settings; the history fingerprint covers regular file names and contents, not filesystem metadata. A complete recovery acceptance still requires testing a recovered API, login, document revision, Knowledge, Evidence and approval workflows and recording measured RPO/RTO.

## Verification status

The disposable CI test uses real rootless Podman and systemd Quadlet units, the pinned PostgreSQL image, age encryption and an isolated PostgreSQL/history restore. It verifies generated Quadlet stop removes the container, the generator-owned `default.target.wants` links stay unchanged, intent conditions skip starts without a unit-specific permit even when only the recovery marker remains, authorized API/Tunnel recovery starts remove their permits, source drift blocks Tunnel restart, and captured runtime identities survive recreation. Narrow `findmnt`, `getent` and `ip` fixtures model an external mount solely to exercise destination gating; a second fixture proves that a loopback NFS source is rejected. It also verifies route/writer/lock rejection, encrypted artifact checksums, recovery-key permissions, restore failure cleanup, an injected Podman removal failure that withholds success and still retries scratch cleanup, and successful fingerprint comparison.

Actual off-VM NFS/CIFS/SSHFS backup, external recipient custody, use of the real recovery key, target-host writer/Tunnel resumption and real recovered API workflows are **NOT_CHECKED** without authorized external destination and recovery access. The disposable CI proof is not production backup or disaster-recovery evidence.
