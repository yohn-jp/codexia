# 復元済み環境の引き渡し案

**設計提案。** R2/R3 の実行手順と、復元済み DB を通常 Backend に引き渡す保全証拠の条件は承認を要する。
既存の [配備ライフサイクル](DEPLOYMENT-LIFECYCLE.md)、[復旧契約](BACKUP.md)、[初回配備](INITIAL-DEPLOYMENT-FLOW.md) が決める状態遷移、承認、単一 writer の制約を適用する。

## 実行面の選択

| 案 | 実行面 | 運用上の差 |
| --- | --- | --- |
| 復旧担当が隔離先を復元し、配備運用者が同じ認定済み Backend handoff で起動する | 既存の独立秘密管理、オペレーター手順、Ansible、保護された production queue | 復号鍵を配備面に渡さず、証拠の照合と公開承認を既存の配備トランザクションで実施できる |
| R3 の手順で同じ VM 上の既存サービスを修復して再起動する | 既存の rootless Quadlet、通常復旧ヘルパー、Ansible | DB、資格情報、認定済み配備状態が残る障害を扱える。VM または DB を喪失した場合は復元が先行する |

復元を要する既存環境には第一案を採ることを提案する。
R3 の同一環境修復は既知の健全な release と DB の組を保持できる場合に適用する。
保全証拠の照合には既存の Preflight と運用記録を使う。
保護された復元素材を扱うのは復旧担当者と隔離先に限り、通常 Backend handoff は証拠の非秘密部分を参照する。

## 復元点と公開承認の照合

1. 復旧担当者は独立保管先のバックアップを選び、保護された運用 receipt の送信元、取得対象、暗号文 digest と照合する。v2 のダウンロード、復号、隔離ドリルで DB と history を確認する。同時に復旧鍵、DB ロール、Podman secrets と外部サービス設定の取得経路を確認する。
2. 対象の明示承認後、配備運用者は既存 Ansible で隔離された復元先の基盤を収束する。復旧担当者は DB、history、資格情報を既存手順で復元する。既存データを収める VM または DB への上書きや復元点以後の書込みの扱いには、対象と失われる範囲を明示した別の操作承認を使う。元の writer が停止した証拠、または同時稼働できない状態の確認を公開の前提にする。
3. 復元先で、選択済みバックアップの内容と PostgreSQL ledger、DB と history の fingerprint、owner と Passkey、OAuth client、認証設定、資格情報の識別子を照合する。論理復元では source と target の PostgreSQL cluster ID や DB OID が変わり得る。source の証拠と、今回の復元先のホスト、cluster ID、DB OID を個別に識別し、同じ復元操作に結び付ける。R3 の同一環境修復では現在の DB と release の既存 identity を照合する。
4. Preflight から公開まで、検証済みの復元先と候補 digest、互換な通常 Frontend、承認期限を同じ保護記録に結び付ける。既存の保全 assertion で使用できる入力と、既存の host lock 下で再照合すべき fingerprint と設定を設計承認時に確定する。R6 は普通の起動経路を再利用し、既存 owner と client で起動する。DB が既知のままの R3 は該当する基盤またはサービスだけを復旧する。
5. readiness、正しい immutable digest、外部の許可と拒否、既存 owner の認証を確認する。公開後は新規に受理した書込みを含む復旧点を決めてから次の復旧操作に移る。保存先の再確認と独立復元の受入は通常 Console と復旧担当者が記録する。

中断時は既存の transaction 記録と現状態を再照合する。
用途が確定しない記録、復元不足、複数 writer の可能性、復元素材の欠落、別のホストや候補に紐付く証拠、期限切れは停止にする。
公開前に失敗した対象は隔離状態に戻し、復元済みデータと記録を保持する。

## 受入証拠

| 検証環境 | 確認する事実 |
| --- | --- |
| 使い捨て VM | 合成した既存 owner と原稿を独立保存から別の PostgreSQL へ復元。以前の環境と異なる cluster ID/OID の場合も、証拠が正しい対象と復元点に結び付く。空 DB の初回登録や既存 owner の再発行に遷移しない |
| 拒否と再開の試験 | 別 source、対象差し替え、保全証拠欠落、候補変更、期限切れ、元 writer が停止していない場合は公開を拒否する。中断後は同じ対象への再検証か、承認済みの復旧を要求する |
| 実環境 | 実際の保存先と独立ホストで復元し、運用者が RPO/RTO、復元点以後の書込み、元 writer 停止、外部経路、owner のログイン、バックアップ運用を受け入れる |

承認時に、既存の運用記録から Preflight と host lock 下の配備へ引き渡す証拠の項目、発行者、保護先を決める。
現時点の [Ansible 隔離ドリル](../../deploy/ansible/restore-drill.yml) は使い捨て資源で終了する。
[通常配備の中断復旧](../../deploy/ansible/push-deployment-recover.sh) は既存の release 状態を対象にしており、独立バックアップから本番へ復元する受入は別に必要になる。
