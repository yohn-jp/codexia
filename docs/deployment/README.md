# Codexia deployment

**Normative lifecycle transitions:** [Deployment lifecycle](DEPLOYMENT-LIFECYCLE.md) owns cross-component state classification, route selection, first Backend activation, maintenance and recovery. [Initial deployment](INITIAL-DEPLOYMENT-FLOW.md) and [Compatible backend update / rollback](UPDATE-FLOW.md) define the required state machines. Runbooks describe how to operate the approved transition; the current script is implementation evidence, not the design authority.

**Protected production entrypoints:** [GitHub Actions Bootstrap workflow](PRODUCTION-BOOTSTRAP.md) handles approved initial host, database and Better Auth convergence. [Push deployment](PUSH-DEPLOYMENT.md) handles independently certified application activation and compatible updates. R5 publishes the certified ordinary Frontend before enrollment; R6 activates only the compatible Backend. An incompatible installed pair is rejected without mutation.

This directory implements the deployable boundary specified by [System design](../architecture/SYSTEM-DESIGN.md) and [Infrastructure as code](IAC.md). The React/Vite application is released as Cloudflare Workers Static Assets. The API is a separate rootless Podman service; Cloudflare Tunnel is its only public origin path.

**Normative initial installation entrypoint:** [codexiactl](CODEXIACTL.md) owns the SSH-side guided authentication, registration, protected dispatch sequence, resume and acceptance contract. Existing workflows remain the execution authority; current manual runbooks remain implementation references until CLI conformance. The official CLI is distributed by `yohn-jp/codexia`; the deployment target is the `codexia` repository discovered and confirmed through the official public GitHub App's user authorization under the [target discovery contract](CODEXIACTL.md#41-github公式-app-による認証配備対象の発見). A fork uses its own reviewed production configuration, protected Environments, exact-source CI/release evidence and deployment resources, without a separate deployment engine.

## Request and release paths

```text
Browser
  -> Cloudflare Access (one hostname and identity policy)
  -> assets-only catch-all -> codexia-frontend Static Assets -> Vite assets
  -> scriptless API/health/MCP exclusions -> Cloudflare Tunnel -> codexia-api container

API browser calls stay on the same hostname at /api/*.
The Worker has no API route and no origin-proxy fallback.
```

The route contract in `deploy/cloudflare/ui-routes.json` assigns a catch-all to the assets-only Worker and more-specific scriptless exclusions to the Tunnel for API, health, MCP and OAuth metadata paths. This also covers query-string root requests. Unknown static paths and missing assets return 404. No Worker script, binding, or Worker-first route is deployed. Static 200 proxies in `edge/frontend/static/_redirects` serve the Desktop and reader shells without executing code at the edge.

Static response headers are defined in `edge/frontend/static/_headers`. The static UI sends host-only HSTS (`max-age=31536000`) without `includeSubDomains` or `preload`; this header does not assert the production zone's current HTTPS/HSTS settings. Script execution is restricted to same-origin external scripts; dynamic CodeMirror styles require inline styles in the static delivery CSP. The API-hosted UI retains per-response style nonces. The static frontend contains no secrets or origin-proxy code. Static asset requests do not incur Worker invocation charges.

## Authentication, API URL, and CORS

Deployments use the embedded Better Auth provider. Follow the [staged first-activation procedure](PUSH-DEPLOYMENT.md) to provision its dedicated database role, enroll the owner Passkey, and register OAuth clients. The [API authorization contract](../architecture/API-AUTHN-AUTHZ.md) and [iOS client guide](IOS-CLIENT.md) describe Web and native authorization.

Cloudflare Access applies the outer identity allowlist to the application hostname. The Tunnel origin also requires the Access application audience. Codexia enforces its API authorization boundary independently.

The current UI uses relative `/api/...` URLs, so production has no `VITE_API_URL` or API-origin secret. UI and API share one origin and no CORS allowlist is configured by default. The OAuth transition supports optional cross-origin Web calls only when an operator configures exact HTTPS origins in `CODEXIA_CORS_ALLOWED_ORIGINS`; those calls are bearer-only, omit browser credentials, and cannot carry cookies. This setting does not change Cloudflare routes or enable a separate API hostname. External MCP/API clients must use their supported authorization flow and do not receive a CORS exception.

### OAuth public Web client

The Web client uses the embedded Better Auth OAuth Provider. Its authorization-server issuer is `${CODEXIA_PUBLIC_ORIGIN}/api/auth`; confirm its published metadata at `/.well-known/oauth-authorization-server/api/auth`. The provider exposes `/api/auth/oauth2/authorize` and `/api/auth/oauth2/token`. The owner signs in to Better Auth with a Passkey or a linked optional OIDC provider. The browser uses the API access token issued by Better Auth. Register the exact Desktop callback on one public Web client with Authorization Code + PKCE S256 and token endpoint auth method `none`. Bind the approved API resource to that client and request `resource` with `openid codexia:api`.

The production frontend build, promotion and deployment read the public origin, Desktop callback, client ID and scopes from the [versioned production configuration](../../deploy/production.json). The build embeds these settings and records their canonical identity. Promotion verifies that identity against the reviewed source configuration. Existing deployed artifacts with the original identity format retain their recorded callback list. For a new deployment, the current artifact and owner setup use the certified Desktop callback. An owner setup already staged against an older artifact remains bound to its approved archive and redirect set.

The browser discovers the authorization and token endpoints from the configured OAuth issuer metadata and checks the issuer, public-client method, code grant, PKCE S256, and authorization-response issuer support before starting sign-in. It validates the one-time OAuth state and issuer callback, keeps the PKCE verifier only in tab-scoped session storage during redirect, and keeps only the Codexia API `access_token` in JavaScript memory. It sends that token as `Authorization: Bearer` for API data requests and omits browser credentials. The client does not request or persist refresh tokens; after access-token expiry or page reload, the user signs in again. Sign-out clears the in-memory bearer and ends the Better Auth browser session; logout alone does not revoke an already-issued access JWT. A client can explicitly revoke one access token through the authenticated RFC 7009 endpoint at `/api/auth/oauth2/revoke`. Revocation is checked by API admission and OAuth introspection; it does not revoke sibling tokens or end the login session. The Better Auth login and consent handoff uses same-origin session operations separately from bearer API data calls.

The official repository's static UI origin is `https://codexia.yohn.jp`; its Access-protected asset delivery stays unchanged. Other deployment repositories must use their own reviewed production origin and corresponding edge resources from their exact certified source. OAuth login currently requires the Better Auth routes and the static `/oauth/login` and `/oauth/consent` UI routes on that same origin. `VITE_CODEXIA_API_ORIGIN` remains unset for the current same-origin route. Cross-origin bearer API calls remain an optional explicit operator configuration, but cross-origin Better Auth login/session behavior is unverified and the existing CORS policy does not permit credentialed cross-origin requests. No separate API hostname has been selected or deployed. The OAuth issuer, API resource, registered client and redirect URIs, any API hostname, exact CORS allowlist, Cloudflare Access application/policy, Tunnel hostname mapping and live authorization acceptance remain operator prerequisites. The client configuration alone does not establish these boundaries.

## Build and release ownership

[CI/CD architecture](../verification/CI-CD.md) owns verification, artifact certification and release admission. The following describes component artifacts, operational configuration and deployment ownership. A successful component build does not by itself authorize publication.

- UI changes build `app/dist` with `pnpm run build:frontend`, check and test the static Worker, then upload only the `codexia-frontend` asset Worker. The release job runs only after a push to the configured base branch and uses the `codexia-production` GitHub Environment. Production UI is built with the Full profile. Zone Routes are operated separately and are never changed by Wrangler.
- Frontend and Backend use independent SemVer bases in `app/package.json` and `packages/api/package.json`. CI adds the component workflow's run number to the base patch. Compatible changes need no version-only commit; intentionally change the major/minor base for a new version line. Local builds retain the declared base. Successful frontend deployment creates an immutable-by-policy `frontend-v<version>` GitHub Release; certified backend publication creates `backend-v<version>` with Core/Full immutable digest references. Release records include the API epoch. Existing release tags and records may not be repointed or replaced. GitHub workflow run numbers are independent, retries keep the same number, and unused PR numbers are harmless gaps.
- The frontend declares its required API epoch in `deploy/frontend-compatibility.json`. Backend advertises its provided epoch in `deploy/update-compatibility.json` and its running `/api/version` response. Independent release versions are compatible exactly when their API epochs and deployment profiles match. For ordinary releases, require a live compatible backend and the appropriate deployed frontend identity. An absent or incompatible identity stops ordinary release admission. Only the protected R5 initial frontend and R6 Backend-only activation have their explicit clean-install admission. Review the HTTPS origin in the production configuration and provision the service token secrets `CODEXIA_ACCESS_CLIENT_ID` / `CODEXIA_ACCESS_CLIENT_SECRET` before activation. CI runs the read-only Production Access Preflight in parallel with the build, daily and on manual dispatch from main; it verifies both identity JSON responses, the candidate's required Full profile and API epoch against the live backend, anonymous denial and CI-token denial on non-probe paths. It reports endpoint, HTTP status and CF-Ray without logging credentials or bodies. A Cloudflare `cf-mitigated: challenge` on an identity path is reported separately as `EDGE_CHALLENGE`, not an Access token failure. Anonymous identity probes must reach the authorization boundary; a geographic challenge on an out-of-scope author route proves external denial only. The production mutation job still rechecks live backend compatibility immediately before replacing the UI. The VM checks the actual deployed UI before replacing the backend. The two identity probe paths and their exact Tunnel regexes are defined in `deploy/cloudflare/identity-probes.json`; their path apps use the reusable CI policy, while normal paths retain only author authorization. A failing preflight blocks frontend replacement, not repository verification or backend artifact publication. API epoch changes that are incompatible with an installed environment stop without mutation.
- Backend changes build `Dockerfile.backend`, test the resulting image, and publish `ghcr.io/<target-owner>/codexia-backend:sha-<40-character-commit>` (the official deployment uses `yohn-jp`; forks use the verified target owner) only after a push to the configured base branch and successful complete main-push verification for that exact commit, including certification. The publication gate waits up to one hour and fails closed if verification is unavailable or unsuccessful. Core retains the existing `sha-<40-character-commit>` tag. Full is independently built and tested in parallel and published as `ghcr.io/<target-owner>/codexia-backend:sha-<40-character-commit>-full` behind the same exact-source gate. Both images contain only the selected API profile and runtime dependencies, not `app/dist`.
- Release lane selection and the common certification gate are defined in [CI/CD architecture](../verification/CI-CD.md).
- The production push job in [Push deployment](PUSH-DEPLOYMENT.md) consumes the exact certified Full digest and provenance certificate after publication. Its protected enable flag stays false until the `codexia` VM account, SSH trust and applicable activation/update checks are accepted. Fresh activation requires no backup destination; ordinary updates require accepted backup and recovery. PR validation never attaches the production Environment or receives Tailnet OIDC credentials. There is no signed pull channel, updater service or timer. Protected push deployment is the sole backend activation path.
- `CLOUDFLARE_API_TOKEN` is only available to the protected production Worker job. `CLOUDFLARE_ACCOUNT_ID` is a GitHub Environment secret. GHCR publication uses the job-scoped `GITHUB_TOKEN` with `packages: write`.

The Cloudflare Terraform example manages the author Access application, two exact-path CI identity applications, remotely managed Tunnel, DNS record, and disabled-by-default UI Routes. Supply account, zone, identity-provider, and the existing account-owned reusable author Allow policy ID (`access_policy_id`) and CI Service Auth policy ID (`access_ci_policy_id`) in a private tfvars file. Follow [Access policy migration](../../deploy/cloudflare/terraform/ACCESS-POLICY-MIGRATION.md) when transitioning an existing deployment; the author allowlist is managed by the account policy owner, not this Terraform configuration. The zone owner must exclude the exact HTTPS identity GET paths from any interactive geographic WAF challenge; the Codexia Terraform module does not own shared zone rules. For `codexia.yohn.jp`, the `OutRage Challenge` rule must preserve its existing non-JP predicate and append `and not (http.host eq "codexia.yohn.jp" and http.request.method eq "GET" and http.request.uri.path in {"/api/version" "/desktop/update-identity.json"})`. Do not skip Access or exempt the full hostname, other HTTP methods, API prefixes or author routes. Confirm the exemption against `identity-probes.json` and the protected preflight. Keep Terraform state in an encrypted remote backend. The operator supplies `CLOUDFLARE_API_TOKEN` locally with only the Tunnel, Access, DNS and Worker Route permissions this configuration needs. Review imports and live state before applying; CI runs `fmt`, `init -backend=false`, and `validate`, never `apply`.

## VM environment and Secrets

[Infrastructure as code](IAC.md) is the normative VM desired-state authority. Rootless host inspection and the protected secret, storage, network, PostgreSQL and Tunnel stages are implemented; the push deployment and encrypted off-VM recovery contracts are defined in [Push deployment](PUSH-DEPLOYMENT.md) and [Backups](BACKUP.md).

`deploy/quadlet/codexia-api.container` defines these runtime values:

| Variable | Owner | Purpose |
| --- | --- | --- |
| `HOST=0.0.0.0` | Container | Listen on the private Podman network. |
| `PORT=3000` | Container | API port consumed by Tunnel. |
| `CODEXIA_PROFILE=core` | Release | Select the immutable server profile packaged into the image. |
| `CODEXIA_DATA_DIR=/data` | VM operator | Derived module caches; project authoring state lives in PostgreSQL. |
| `CODEXIA_USAGE_DIR=/history` | VM operator | Persistent usage/job history. |
| `CODEXIA_DATABASE_MIGRATE_ON_START=0` | VM operator | Keep schema migration outside service startup; image activation requires a pre-initialized and compatible database. |
| `CODEXIA_DATABASE_PASSWORD_FILE` | Podman secret | Startup reads the hexadecimal `codexia` application-role password and builds the private service connection URL. |
| `CODEXIA_TRUST_PROXY=1` | Origin boundary | Honor HTTPS forwarding only because the API has no published host port and is reachable through the configured Tunnel. |

Create `codexia-tunnel-token`, `codexia-postgres-admin-password`, and `codexia-postgres-app-password` as rootless Podman secrets from protected files on the VM. Use independent 32-byte hexadecimal database passwords. PostgreSQL initializes a private `codexia_admin` superuser and a separate `codexia` application role that owns the application database; both database secrets are mounted in PostgreSQL for initialization of the separate roles; only the application secret is mounted in the API. Copy `deploy/postgres/010-create-app-role.sh` to `/etc/codexia/postgres/010-create-app-role.sh` before the first database start so the official image can create the least-privileged application role. Ansible installs the canonical, credential-free initializer as mode `0555` inside the service-owned `0750` directory: the rootless container maps the host service owner to container root, so the PostgreSQL UID requires other-read and execute on the read-only bind. Passwords remain in Podman secrets. The Tunnel token and database passwords must not appear in Quadlet text, shell history, Terraform outputs, or logs. The API has no published host port; Tunnel metrics are the only host binding and remain loopback-only. The API and PostgreSQL share the internal-only `codexia-data` network; the Tunnel cannot reach the database. The separate `codexia` network lets the Tunnel reach the API.

Install the `.container`, `.network`, and `.volume` files in the rootless service account's `~/.config/containers/systemd/` directory. Run `systemctl --user daemon-reload`; the protected Ansible `deploy` stage activates the API only after the database is initialized or verified and compatible. Quadlet services are generated units and cannot be enabled with `systemctl enable`; their `[Install] WantedBy=default.target` sections make them start with the user's default target. Configure systemd lingering for that service account so its user services survive logout and start at boot. The `codexia-api.service` dependency starts after `codexia-db.service`, which uses the persistent `codexia-postgres` volume. The API Quadlet keeps startup schema migration disabled. Before the first activation, Ansible initializes a pristine application schema during auth staging and verifies the exact ledger again before starting the certified image; subsequent schema changes to a nonempty database remain unsupported until a separately approved backup, migration, verification, and restore procedure is accepted. The API reports ready only while PostgreSQL answers health checks. The API and database have no host ports. Tunnel metrics bind to `0.0.0.0:2000` inside its private network but publish only as `127.0.0.1:2000` on the VM; they are not reachable from the Internet.

The Worker build has no runtime secret and no API-origin variable. The Cloudflare token exists only in the GitHub production environment. Cloudflare Access emails and IdP IDs are configuration, not authentication secrets.

## Health and recovery

The API exposes unauthenticated process probes at `/health/startup`, `/health/live`, and `/health/ready`; `/api/ready` also reports request draining. Quadlet checks `/health/ready` from inside the API container. `cloudflared` exposes `/ready` and Prometheus metrics on port 2000; from the VM, `curl --fail http://127.0.0.1:2000/ready` checks for an active Cloudflare edge connection, while systemd restarts an exited tunnel process. The operator checks connection status in the Cloudflare dashboard and owns alerting from the VM-local metrics endpoint. No service endpoint or metrics port is exposed to the Internet.

### Persistence and backups

All workspaces use PostgreSQL as their canonical project, document, revision, Knowledge, and Evidence store. The schema is applied from the API image's existing checksum-verified migrations before the API accepts traffic. Use the explicit migration tooling to import an existing manuscript before opening it. Browser recovery drafts are local to their browser profile and remain separate from the database.

PostgreSQL uses the persistent `codexia-postgres` volume on an internal-only Podman network. Follow the [encrypted backup and isolated restore procedures](BACKUP.md) for the PostgreSQL database and `codexia-history` volume. The protected host transaction quiesces the writer and uses the canonical backup producer under the host lock. The operator retains an independent off-VM copy, verifies recovery on an isolated host, and maintains separate recovery material for database roles, secrets and keys.

The [backup control plane](../../deploy/backup/CONSOLE.md) supports operator-provisioned S3-compatible destinations and the existing encrypted artifacts. The [owner backup screens](../design/ADMIN-SCREEN-FLOW.md) provide configuration, verification, backup requests, and evidence when the control plane is provisioned. Disaster-recovery acceptance requires verified transfer and readback at the actual storage destination and a restore drill on an independent host. [Backup acceptance](BACKUP.md#受入シナリオ)

The `codexia-data` volume (`/data`) holds derived module caches that can be rebuilt. Retain the prior API image tag and origin UI image until rollback is rehearsed.

[Protected recovery handoff](PROTECTED-RECOVERY.md) defines the evidence required for the approved R2 restore and R3 publication through the existing deployment path.

## Rollback and live acceptance

Keep the last origin image that still contains the UI until static delivery and Access behavior are proven. Terraform's `frontend_route_enabled=false` removes the static catch-all and its scriptless exclusions; all requests then reach the Tunnel. Rollback restores the retained origin image, disables the UI routes, and checks API login, write CSRF protection, Access denial, static 404 behavior, and an authenticated UI session.

Before setting `frontend_route_enabled=true`, validate Access on both the Worker routes and Tunnel origin. Test Access denial, API login and write CSRF protection, authenticated UI/API use, static asset 404 behavior, Tunnel readiness, and rollback. Keep the last origin image until the new route and identity behavior pass those checks. To roll back, set `frontend_route_enabled=false`, restore the retained origin image, and verify the UI and API again.
