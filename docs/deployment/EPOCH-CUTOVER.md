# Protected API epoch 1 → 2 maintenance

The [coordinated cutover contract](PUSH-DEPLOYMENT.md#coordinated-api-epoch-cutover) governs this workflow. Use [Coordinated API epoch maintenance](../../.github/workflows/production-epoch-cutover.yml) from main and approve each mutation in the protected production Environment. The in-place workflow requires an installed Full epoch 1 release on persistence format 1, an existing Better Auth owner, and the same packaged SQL ledger on both images. If the old account still uses token authentication, follow the design's separately approved clean-target enrollment and data-transfer procedure. A missing owner or unsupported ledger blocks this workflow.

## Prepare the protected target

- Retain the old static archive and deployed Worker UUID, the exact old Full digest, the installed Quadlet and hashed auth settings, and the separately recoverable PostgreSQL roles and Podman secrets. Verify that both releases have a usable source and archive record.
- Use the existing Access probe token, Tailnet OIDC setup, pinned SSH identity, backup directory and public age recipient. The independent recovery host holds the private age identity.
- Have the Cloudflare zone owner install a disabled custom block rule in first position with ref `codexia-epoch-cutover` and description `Codexia maintenance fence`. Use the exact expression computed by `buildFenceExpression(origin, acceptance)` and the response exported as `FENCE_RESPONSE` in [the Cloudflare adapter](../../scripts/release/cutover/cloudflare.mjs). Reconcile this rule with the zone's infrastructure management before approval. Confirm the target has no alternate public entry through zone/account allow rules, sibling Worker proxies, Snippets or another Tunnel. The adapter checks the expected Access and Tunnel routing, rule definition, public denial, and disabled Worker preview hostnames.
- Set `CODEXIA_CUTOVER_CLOUDFLARE_TARGET` as a protected JSON variable with `accountId`, `zoneId`, `tunnelId`, `fenceRuleId`, `authorPolicyId`, `ciPolicyId`, `tunnelTeamName`, `publicProtocolEnabled` and `acceptance`. Each acceptance entry has `ip`, `method` and exact `path`. Use only the reviewed tester address and the routes required for acceptance. Existing Access decisions still apply.
- Use separate protected secrets for `CODEXIA_CUTOVER_CLOUDFLARE_READ_TOKEN`, `CODEXIA_CUTOVER_WORKER_TOKEN` and `CODEXIA_CUTOVER_FENCE_TOKEN`. Scope read access to the targeted account and zone's Workers, routes, DNS, Tunnel, Access apps and policies, WAF and IP Access rules. The two write credentials are for version uploads and deployments, and for the approved rule toggle, respectively.
- After the review, enable `CODEXIA_EPOCH_CUTOVER_ENABLED`. Before starting the maintenance window set `CODEXIA_EPOCH_CUTOVER_PAUSED=true`, then confirm the ordinary deployment jobs are blocked. All mutation jobs serialize on the same production queue. Keep the pause through completion or verified recovery.

## Phase requests

Dispatch `preflight` with the installed backend's `priorBackendPublisherRunId`. Its redacted evidence identifies the host, actual writer and authenticated publication certificate, database cluster and ledger, public backend and frontend identities, and the Cloudflare topology and current Worker deployment. Check `ready` and retain the run evidence under the approved maintenance record.

Dispatch `stage` with `priorBackendPublisherRunId`, `backendPublisherRunId`, `priorArchiveSha256`, `ingressReviewSha256` for the retained review of alternate ingress, `frontend` containing the main producer's `runId`, `verifyRunId`, `artifactId` and raw `artifactDigest`, and `window` containing `id`, `notBefore` and `notAfter` as UTC ISO timestamps with milliseconds. Select the completed main frontend run and its successful build job even if the independent production deployment failed. The workflow verifies both authenticated backend publication certificates, their immutable images and the exact main frontend archive, stages the candidate Quadlet under a private path, and uploads a Worker version with no traffic. Review both releases, topology, the window and the returned plan SHA-256.

For subsequent phases pass the exact returned `plan` object and its `planSha256` as `approval`. Approve the window and the evidence digest through the protected Environment. Phase inputs and uploaded artifacts contain only the redacted plan and proof identifiers. Store raw evidence and credentials in their approved protected locations.

1. Dispatch `checkpoint`. The workflow verifies the fence, stops the Tunnel and writer, and records the canonical encrypted backup and database/history fingerprints. The host transaction blocks automatic restarts across disconnects and reboots while they are required to stay stopped.
2. Copy the exact encrypted artifact to independent recovery storage and verify that copy. On the separate recovery host, run [the recovery receipt producer](../../scripts/deployment/recovery/epoch-cutover.mjs) with the checkpoint binding, reviewed window, age identity, and protected evidence records for the off-VM copy, PostgreSQL roles, Podman secrets, prior owner authentication and restore procedure. The receipt producer runs the existing isolated restore and conversion drill. Put the resulting JSON in the protected `CODEXIA_CUTOVER_RECOVERY_RECEIPT` secret.
3. Dispatch `apply`. The host rechecks the checkpoint, performs only the needed format conversion using the staged Full image, and starts the candidate API while the Tunnel and ingress remain closed.
4. Dispatch `promote`. The host starts the Tunnel behind the fence. The protected job activates the staged Worker at 100% and checks the paired identities, original owner binding, exact ledger and database cluster. Conduct the restricted functional acceptance immediately afterwards.
5. Record protected evidence for owner login, Passkey, OAuth, manuscript and history continuity, permission denial and Access boundary behavior. Set `CODEXIA_CUTOVER_ACCEPTANCE` to a JSON object with `format: "codexia-cutover-functional-acceptance/v1"`, `planSha256`, `outcome`, `origin`, `image`, `workerVersion`, `verifiedAt`, and a `checks` object. Its raw SHA-256 values identify separate retained evidence for `ownerLogin`, `passkey`, `oauth`, `manuscript`, `history`, `permissionDenial` and `accessBoundary`. Use a time after both the Tunnel and selected Worker were active.
6. Dispatch `finish` with `outcome: "candidate"`. The workflow verifies the acceptance and live pair, reopens ingress, confirms the maintenance block is gone while Access remains enforced, and commits the durable release record. Only then resume ordinary releases and transfer the redacted run evidence, exact digests and source SHAs to [#168](https://github.com/yohn-jp/codexia/issues/168).

## Interruption and recovery

Keep the protected pause and ingress fence in place. If the checkpoint failed before the writer stopped, check the preceding run and live identities, then retry the exact checkpoint. If the fence is active and no host intent was created, gather the prior pair's protected functional acceptance and dispatch `abort-fence`. Reopening requires the same prior container, Quadlet, database and Worker. Once a host intent exists, use the same plan for recovery. If conversion was interrupted or the candidate fails verification, dispatch `recover-quiesce`. This stops the writer and Tunnel and restores the old Worker at 100% inside the fence.

If the host marks `requiresRestore`, restore the exact verified pre-change PostgreSQL and history data and any required prior auth config with the separately reviewed recovery procedure. Keep the existing PostgreSQL cluster, owner, roles and runtime secrets. These operations are run by the authorized recovery operator under the canonical host lock, while both services remain stopped. Verify the resulting data and roles against the isolated rehearsal. Set protected `CODEXIA_CUTOVER_RESTORE_RECEIPT` with `format: "codexia-cutover-restoration/v1"`, `planSha256`, `verifiedAt`, the checkpoint's `checksumManifestSha256`, `databaseFingerprint` and `historyFingerprint`, and `procedureEvidenceSha256` for the retained recovery record.

Dispatch `recover`. The host verifies the old image, exact authentication configuration, ledger, and, when applicable, the restored DB/history fingerprints before bringing the old writer online. Repeat functional acceptance on the old pair behind the fence, then dispatch `finish` with `outcome: "prior"`. Retain the evidence from the attempted transition and recovery. The independent disposable fixture verifies code paths using test data and a local issuer. Production Cloudflare, recovery-host independence and physical-device results remain with [#168](https://github.com/yohn-jp/codexia/issues/168).
