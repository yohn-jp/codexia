# Protected production pair activation and cutover

Use [Coordinated production pair maintenance](../../.github/workflows/production-epoch-cutover.yml) on protected main for initial pair activation (R6) and coordinated updates (R3/R7). The [deployment lifecycle](DEPLOYMENT-LIFECYCLE.md#共通制御と個別移行の境界) defines the common controls. The registered in-place format migration preserves the installed Better Auth owner and SQL ledger while converting persistence format 1 to 2. Future incompatible releases require an explicit transition contract and its fixture. SQL ledger and Auth changes require a separately registered procedure.

For first activation, finish the [protected owner preparation](../../deploy/ansible/AUTH-RUNTIME.md#first-owner-through-the-browser), confirm the API slot is clean, and enable both protected first-install and database-use approvals. Prepare the private Worker and canonical routes through the owning Cloudflare infrastructure path before planning. A prepared Worker may have no active deployment. The first activation uses the enrolled owner and does not issue setup grants. Legacy token data transfer requires its own registered migration and separate clean target.

## Prepare the protected target

- Retain the old static archive and deployed Worker UUID, the exact old Full digest, the installed Quadlet and hashed auth settings, and the separately recoverable PostgreSQL roles and Podman secrets. Verify that both releases have a usable source and archive record.
- Use the existing Access probe token, Tailnet OIDC setup, pinned SSH identity, backup directory and public age recipient. The independent recovery host holds the private age identity.
- Have the Cloudflare zone owner install a disabled custom block rule in first position with ref `codexia-epoch-cutover` and description `Codexia maintenance fence`. Use the exact expression computed by `buildFenceExpression(origin, acceptance)` and the response exported as `FENCE_RESPONSE` in [the Cloudflare adapter](../../scripts/release/cutover/cloudflare.mjs). Reconcile this rule with the zone's infrastructure management before approval. Confirm the target has no alternate public entry through zone/account allow rules, sibling Worker proxies, Snippets or another Tunnel. The adapter checks the expected Access and Tunnel routing, rule definition, public denial, and disabled Worker preview hostnames.
- Set `CODEXIA_CUTOVER_CLOUDFLARE_TARGET` as a protected JSON variable with `accountId`, `zoneId`, `tunnelId`, `fenceRuleId`, `authorPolicyId`, `ciPolicyId`, `tunnelTeamName`, `publicProtocolEnabled` and `acceptance`. Each acceptance entry has `ip`, `method` and exact `path`. Use only the reviewed tester address and the routes required for acceptance. Existing Access decisions still apply.
- Use separate protected secrets for `CODEXIA_CUTOVER_CLOUDFLARE_READ_TOKEN`, `CODEXIA_CUTOVER_WORKER_TOKEN` and `CODEXIA_CUTOVER_FENCE_TOKEN`. Scope read access to the targeted account and zone's Workers, routes, DNS, Tunnel, Access apps and policies, WAF and IP Access rules. The two write credentials are for version uploads and deployments, and for the approved rule toggle, respectively.
- After the review, enable `CODEXIA_EPOCH_CUTOVER_ENABLED`. Before starting the maintenance window set the repository-level variable `CODEXIA_EPOCH_CUTOVER_PAUSED=true` (no environment-level overrides in either `codexia-production` or `codexia-bootstrap`), then confirm ordinary deployment and bootstrap mutation jobs are blocked. The host also rejects ordinary convergence while the durable cutover journal exists, independently of the variable. All mutation jobs serialize on the same production queue. Keep the pause through completion or verified recovery.

## Plan and stage

For a plan that requires preservation, the preservation authority records the prior independent backup evidence in the protected `CODEXIA_CUTOVER_PRESERVATION` secret. Use `format: "codexia-cutover-preservation/v1"`, `sourceHostId`, `databaseSha256` from the read-only lifecycle observation, and `independentBackupEvidenceSha256` identifying the retained off-VM proof. Run [Production Access Preflight](../../.github/workflows/production-preflight.yml) with `mode=lifecycle` and `management=runtime` to bind this evidence into the plan. The checkpoint still produces an exact fresh backup and requires separate protected recovery evidence before applying changes.

Review the plan, candidate route, artifact identities, source, maintenance window, and required grants. Resolve any Preflight blocker other than `approval-required` before calling the mutation workflow. Dispatch `stage` with:

- `deployment` containing `plan`, `planSha256`, and `approval: { planSha256, grants }`, where `grants` names the actual protected approvals from the plan.
- `artifacts` containing `backendPublisherRunId`, `priorBackendPublisherRunId` when an API is installed, and `frontend` with `runId`, `verifyRunId`, `artifactId` and raw `artifactDigest` as in Preflight.
- `priorArchiveSha256` for a deployed Worker and `ingressReviewSha256` for the independent review of alternate ingress.

The protected job re-observes the source and independently verifies both candidate artifacts and the installed Backend certificate when present. It stages only changed components. Review the staged result and use its exact `plan` and the returned digest as `approval` for subsequent dispatches. The first host mutation rechecks this staged plan and saves admission to the host journal before fencing public ingress.

## Advance and publish

1. Dispatch `advance`. The executor verifies the fence and advances through the required checkpoints. When preservation is required, it stops at `awaiting-independent-recovery-proof` with a binding for the encrypted checkpoint. The durable host controls keep services stopped while required across disconnects or reboots.
2. Copy that exact encrypted artifact to independent storage. Run the [recovery receipt producer](../../scripts/deployment/recovery/epoch-cutover.mjs) with the checkpoint binding, reviewed window, age identity, and protected evidence records for the copy, PostgreSQL roles, Podman secrets, owner authentication and restore or safe-stop procedure. On first activation, the owner-authentication record refers to the prepared owner. The drill verifies the restored data and performs a conversion rehearsal only for a registered conversion. Store the receipt in `CODEXIA_CUTOVER_RECOVERY_RECEIPT` and resume `advance` with the same staged plan.
3. The executor applies only the registered migration, verifies the running API, promotes the changed Worker behind the fence, and stops at `awaiting-functional-acceptance`. Verify the exact pair under the approved restricted acceptance routes.
4. Store protected acceptance in `CODEXIA_CUTOVER_ACCEPTANCE`. Use `format: "codexia-cutover-functional-acceptance/v1"`, the staged `planSha256`, `outcome` (`candidate` or `prior`), `origin`, `image`, `workerVersion`, `verifiedAt`, and a `checks` object. The checks are the raw SHA-256 evidence identifiers for `ownerLogin`, `passkey`, `oauth`, `manuscript`, `history`, `permissionDenial` and `accessBoundary`. Use a timestamp after both the Tunnel and selected Worker were active.
5. Resume `advance`. The executor records publication intent before lifting the fence, verifies the live boundary and pair, then commits the host release record. Clear the pause after the release or verified recovery is recorded. Retain redacted evidence with the production acceptance record.

## Interruption and recovery

Keep the production pause and fence in place. Resume `advance` on the same plan when the journal records a known forward checkpoint, including an interrupted stop before the backup was committed. A conversion or candidate startup interrupted after its write intent requires protected recovery.

Dispatch `recover` with the same staged plan. The executor fences and quiesces the host. If the host requires restoration, it returns `awaiting-restoration`. An authorized recovery operator uses the canonical host lock, verifies the exact prior backup, restores as prescribed, and verifies the database, history, roles and secrets while the services stay stopped. Store `CODEXIA_CUTOVER_RESTORE_RECEIPT` with `format: "codexia-cutover-restoration/v1"`, staged `planSha256`, `verifiedAt`, `checksumManifestSha256`, `databaseFingerprint`, `historyFingerprint`, and `procedureEvidenceSha256`.

Resume `recover`. For an installed pair, the executor verifies the restored prior identities and runs the restricted prior acceptance before reopening. Upload fresh acceptance with `outcome: "prior"` and resume `recover` to publish that outcome. Without a complete prior pair, recovery retains the database and owner and leaves public ingress fenced.

After the publication checkpoint, ordinary rollback is blocked because new writes may have reached the database. Use `reconcile` with the same plan and protected acceptance to verify and finish the recorded outcome. A later data restore requires a new recovery plan that accounts for the writes since publication.
