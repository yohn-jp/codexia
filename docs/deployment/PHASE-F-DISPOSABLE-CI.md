# Standalone updater acceptance

The manual-only [Standalone updater acceptance workflow](../../.github/workflows/standalone-updater-acceptance.yml) runs the host and base Ansible integration scripts, an Ansible application lifecycle, then a disposable rootless Podman/systemd updater lifecycle on the same Ubuntu 26.04 runner VM. Host, secrets and base assertions reuse one Ansible-created service identity. After those fixtures clean their resources, the application scenario uses a separate resource set under that same identity: it runs real Ansible secrets, base, prepare and initialize-schema; starts an exact certified legacy API against the initialized PostgreSQL/data/history volumes; creates a project through that API; and runs Ansible `bootstrap-preflight` with a distinct forward release. An injected runtime setting must be rejected while the old writer remains active and the private route remains blocked. The fixture then removes only that disposable legacy service and activates the fresh controller over the same database and volumes, proving that the API-created project persists. This exercises the cutover candidate verifier and drift denial, not the backup-gated cutover transaction; that operation requires the existing off-VM backup proof and isolated restore receipt, which this fixture does not manufacture. The lifecycle continues with enable→pause→resume using a loopback TLS identity server and synthetic Access headers. Those checks prove stage mechanics only and do not claim real public identity or Access acceptance. Finally, it restarts the rootless user manager and verifies the boot recovery unit and Ansible `initialize` against the committed writer, route, PostgreSQL identity and project. The VM itself is not rebooted. The later signed updater lifecycle uses its own isolated service identity and state. The workflow is not a routine PR or main-push check; run it explicitly for release/migration acceptance when the updater lifecycle or compatibility contract changes. It does not call the Full-model OCI workflow: the canonical Verify impact plan and standalone Full-model workflow already own that proof. Both runtime scenarios use the production locked controller with exact certified backend image digests. A fresh ephemeral Ed25519 key signs only the temporary channel fixture; it validates signature and update mechanics, not production publisher authority. The channel and frontend identity URLs are simulated by a process-scoped Node preload that intercepts those two exact URLs. Every other request uses Node's original `fetch`.

The updater lifecycle script verifies release tags, direct source commits, successful exact-source `verify.yml` and `backend-release.yml` jobs, pulled GHCR digests, OCI source labels, embedded backend identities, and packaged migration fingerprints. Before starting PostgreSQL, it records the disposable service account and host file ownership/mode, the rootless Podman and container UID/GID maps, and a read-only access check against the exact pinned PostgreSQL image and init-script bind. The `postgres-init-access.txt` artifact contains those diagnostics without secret values. The updater script then initializes a new disposable database, creates an API project, performs a signed update and rollback, checks container/volume identities and project persistence, kills the updater after the old writer stops, runs boot recovery, and checks that route-state drift is rejected while the proxy returns 503. The Ansible continuity and signed updater lifecycle use separate application resources; the latter is not the Ansible application fixture.

The workflow uploads `ansible-convergence-results.json`, `app-convergence-results.json` and the signed updater evidence without private signing key material. The Ansible records bind their results to the source SHA, workflow run, runner and service UID; the app record also includes observed runtime identities, the legacy-created project ID and user-manager restart result. Production publisher authority, public identity, Cloudflare Access policy, human author UI, VM-level reboot, complete serving-host drift reconciliation, external backup custody, remote recovery/RPO/RTO and successful backup-gated D cutover remain `NOT_CHECKED`. This disposable proof does not close #183 or replace target-host acceptance.
