# Standalone updater acceptance

The manual-only [Standalone updater acceptance workflow](../../.github/workflows/standalone-updater-acceptance.yml) provides a disposable rootless Podman/systemd lifecycle proof. It is not a routine PR or main-push check; run it explicitly for release/migration acceptance when the updater lifecycle or compatibility contract changes. It does not call the Full-model OCI workflow: the canonical Verify impact plan and standalone Full-model workflow already own that proof. It exercises the production locked updater and controller with exact certified backend image digests. A fresh ephemeral Ed25519 key signs only the temporary channel fixture; it validates signature and update mechanics, not production publisher authority. The channel and frontend identity URLs are simulated by a process-scoped Node preload that intercepts those two exact URLs. Every other request uses Node's original `fetch`.

The updater job verifies release tags, direct source commits, successful exact-source `verify.yml` and `backend-release.yml` jobs, pulled GHCR digests, OCI source labels, embedded backend identities, and packaged migration fingerprints. Before starting PostgreSQL, it records the disposable service account and host file ownership/mode, the rootless Podman and container UID/GID maps, and a read-only access check against the exact pinned PostgreSQL image and init-script bind. The `postgres-init-access.txt` artifact contains those diagnostics without secret values. The job then initializes a new disposable database, creates an API project, performs a signed update and rollback, checks container/volume identities and project persistence, kills the updater after the old writer stops, runs boot recovery, and checks that route-state drift is rejected while the proxy returns 503. It does not execute the Ansible lifecycle or start from an existing deployment.

The workflow uploads JSON evidence without private signing key material. The result artifact labels production channel authority, public identity, Access, author UI, VM reboot, remote recovery/RPO/RTO, and D cutover as `NOT_CHECKED`. The manual lifecycle job and the separate canonical CI jobs provide supplemental evidence; they do not close #183 or replace target-host acceptance.
