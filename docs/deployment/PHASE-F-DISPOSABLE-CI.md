# Standalone updater acceptance

The manual-only [Standalone updater acceptance workflow](../../.github/workflows/standalone-updater-acceptance.yml) runs the host and base Ansible integration scripts, then a disposable rootless Podman/systemd updater lifecycle proof on the same Ubuntu 26.04 runner. The host, secrets and base stages reuse one Ansible-created service identity and one rootless account; the base runtime script exercises fresh/repeated convergence, PostgreSQL data adoption and drift refusal before cleaning its runtime fixture. The later signed updater lifecycle uses its own isolated service identity and state. The workflow is not a routine PR or main-push check; run it explicitly for release/migration acceptance when the updater lifecycle or compatibility contract changes. It does not call the Full-model OCI workflow: the canonical Verify impact plan and standalone Full-model workflow already own that proof. The updater test exercises the production locked controller with exact certified backend image digests. A fresh ephemeral Ed25519 key signs only the temporary channel fixture; it validates signature and update mechanics, not production publisher authority. The channel and frontend identity URLs are simulated by a process-scoped Node preload that intercepts those two exact URLs. Every other request uses Node's original `fetch`.

The updater lifecycle script verifies release tags, direct source commits, successful exact-source `verify.yml` and `backend-release.yml` jobs, pulled GHCR digests, OCI source labels, embedded backend identities, and packaged migration fingerprints. Before starting PostgreSQL, it records the disposable service account and host file ownership/mode, the rootless Podman and container UID/GID maps, and a read-only access check against the exact pinned PostgreSQL image and init-script bind. The `postgres-init-access.txt` artifact contains those diagnostics without secret values. The updater script then initializes a new disposable database, creates an API project, performs a signed update and rollback, checks container/volume identities and project persistence, kills the updater after the old writer stops, runs boot recovery, and checks that route-state drift is rejected while the proxy returns 503. The Ansible host/base fixture and updater lifecycle use separate resource states; the workflow does not claim continuous Ansible prepare, activation or D cutover of the updater fixture.

## Acceptance map

| #183 acceptance item | Evidence from these CI jobs | Status boundary |
| --- | --- | --- |
| Fresh and repeated Ansible apply | The manual Phase F run executes the real host stage, secrets stage, and base runtime stage in order using the same service identity on one disposable Ubuntu runner. Each stage proves its first apply and a no-change repeat. | Partial: Ansible `prepare`, schema initialization, first activation, enable and D cutover are not one continuous application convergence. |
| Existing deployment adoption | The same service identity and base fixture exercise PostgreSQL volume and schema/data adoption through the normal Ansible base stage, plus database role/secret and Tunnel checks. | Partial: this is base-resource adoption, not adoption of a complete serving application deployment. |
| Reboot | No Phase F job reboots its runner or exercises a target VM reboot. | NOT_CHECKED |
| Signed update, rollback, interruption, recovery | The Phase F updater job uses rootless Podman/systemd, real source-certified digest-pinned images, signed temporary channel snapshots, and the existing locked updater/controller. | Proven only for the disposable runner and simulated channel/frontend identity endpoints. |
| Full model workload | The existing Verify impact plan selects the pinned Full-model lifecycle proof for affected PR source; its own workflow handles matching main pushes or manual dispatch. | Separate exact-head CI job; its artifact remains distinct from updater evidence. |
| External identity, Access denial, and human author UI | The updater job uses token authentication and a fixture frontend identity. Production preflight is main-only and is not invoked by this PR workflow. | NOT_CHECKED |
| Encrypted backup and isolated restore | This workflow does not perform backup or restore. Reference the separate Phase E exact-head evidence when that workflow is available. | NOT_CHECKED here |
| Remote recovery host, measured RPO/RTO | No remote destination or recovery host is provisioned in CI. | NOT_CHECKED |
| Whole-host drift and D cutover | The base stage refuses existing resource/schema/secret drift through normal Ansible entry points; the signed updater job separately rejects route-state drift. | Partial: complete serving-host drift reconciliation, D cutover and Terraform/Cloudflare handoff remain NOT_CHECKED. |

The workflow uploads `ansible-convergence-results.json` and the signed updater evidence without private signing key material. The Ansible record binds host→secrets→base results to the same source SHA, workflow run, runner and service UID. Production publisher authority, public identity, Access denial, human author UI, actual target-VM reboot, remote recovery/RPO/RTO and production D cutover remain `NOT_CHECKED`. This disposable proof does not close #183 or replace target-host acceptance.
