# Standalone updater acceptance

The manual-only [Standalone updater acceptance workflow](../../.github/workflows/standalone-updater-acceptance.yml) runs the host and base Ansible integration scripts, a clean whole-app Ansible initialization sequence, then a disposable rootless Podman/systemd updater lifecycle proof on the same Ubuntu 26.04 runner. Host, secrets and base assertions reuse one Ansible-created service identity. After those fixtures clean their resources, the application scenario creates a separate clean resource set under that same identity and runs real Ansible secrets, base, prepare, initialize-schema and initialize-fresh stages, including repeats on the same PostgreSQL container, cluster, and persistent volumes. It also exercises Ansible enable→pause using a loopback TLS identity server and synthetic Access headers; this checks stage mechanics only and does not claim real public identity or Access acceptance. This is fresh initialization; it does not claim adoption of an already-serving application. The later signed updater lifecycle uses its own isolated service identity and state. The workflow is not a routine PR or main-push check; run it explicitly for release/migration acceptance when the updater lifecycle or compatibility contract changes. It does not call the Full-model OCI workflow: the canonical Verify impact plan and standalone Full-model workflow already own that proof. Both runtime scenarios use the production locked controller with exact certified backend image digests. A fresh ephemeral Ed25519 key signs only the temporary channel fixture; it validates signature and update mechanics, not production publisher authority. The channel and frontend identity URLs are simulated by a process-scoped Node preload that intercepts those two exact URLs. Every other request uses Node's original `fetch`.

The updater lifecycle script verifies release tags, direct source commits, successful exact-source `verify.yml` and `backend-release.yml` jobs, pulled GHCR digests, OCI source labels, embedded backend identities, and packaged migration fingerprints. Before starting PostgreSQL, it records the disposable service account and host file ownership/mode, the rootless Podman and container UID/GID maps, and a read-only access check against the exact pinned PostgreSQL image and init-script bind. The `postgres-init-access.txt` artifact contains those diagnostics without secret values. The updater script then initializes a new disposable database, creates an API project, performs a signed update and rollback, checks container/volume identities and project persistence, kills the updater after the old writer stops, runs boot recovery, and checks that route-state drift is rejected while the proxy returns 503. The Ansible continuity and signed updater lifecycle use separate application resources; the latter is not the Ansible application fixture.

## Acceptance map

| --- | --- | --- |
| Fresh and repeated Ansible apply | The manual Phase F run first executes the real host stage, then runs secrets and base on one service identity. After base-resource tests clean their fixture, a second clean resource set on that same identity runs secrets→base→prepare→initialize-schema→initialize-fresh with actual repeats, then synthetic loopback enable→pause. It compares PostgreSQL container, cluster system identifier, volume mountpoints, migration ledger, writer/proxy IDs, data volumes and a project created through the API. | Partial: long-running polling, D cutover, reboot, real public Access and complete serving-host adoption are not checked. |
| Existing deployment adoption | The first base runtime fixture exercises PostgreSQL volume and schema/data adoption through the normal Ansible base stage, plus database role/secret and Tunnel drift checks. | Reboot | No Phase F job reboots its runner or exercises a target VM reboot. | NOT_CHECKED |
| Signed update, rollback, interruption, recovery | The Phase F updater job uses rootless Podman/systemd, real source-certified digest-pinned images, signed temporary channel snapshots, and the existing locked updater/controller. | Proven only for the disposable runner and simulated channel/frontend identity endpoints. |
| Full model workload | The existing Verify impact plan selects the pinned Full-model lifecycle proof for affected PR source; its own workflow handles matching main pushes or manual dispatch. | Separate exact-head CI job; its artifact remains distinct from updater evidence. |
| External identity, Access denial, and human author UI | The application scenario exercises a loopback TLS /api/version endpoint: missing synthetic Access headers receive 403, exact fixture credentials receive 200, and Ansible enable verifies the fixture's API identity. The updater job separately uses token authentication and a fixture frontend identity. Production preflight is main-only and is not invoked by this PR workflow. | NOT_CHECKED for external identity, Cloudflare Access policy/denial, and human author UI. |
| Encrypted backup and isolated restore | This workflow does not perform backup or restore. Reference the separate Phase E exact-head evidence when that workflow is available. | NOT_CHECKED here |
| Remote recovery host, measured RPO/RTO | No remote destination or recovery host is provisioned in CI. | NOT_CHECKED |
| Whole-host drift and D cutover | The base stage refuses existing resource/schema/secret drift through normal Ansible entry points; the signed updater job separately rejects route-state drift. | Partial: complete serving-host drift reconciliation, D cutover and Terraform/Cloudflare handoff remain NOT_CHECKED. |

The workflow uploads `ansible-convergence-results.json`, `app-convergence-results.json` and the signed updater evidence without private signing key material. The Ansible records bind their results to the source SHA, workflow run, runner and service UID; the app record also includes observed synthetic runtime identities and the API-created project ID. Production publisher authority, public identity, Access denial, human author UI, actual target-VM reboot, remote recovery/RPO/RTO, full application adoption and production D cutover remain `NOT_CHECKED`. This disposable proof does not close #183 or replace target-host acceptance.
